## Requirement understanding

One line: Add production-ready CRUD (list/query with filter+pagination, get, create, update, delete) for records within a specified MSPbots Form, plus a dedicated read-only record-lookup tool for dropdown/cascading data sources, preserving tenant-level authorization and the form's own validation rules, for the Ginko organization-mapping migration.

The MSPbots Forms MCP today only supports building/publishing forms and reading back submitted responses (a list view and an aggregate-stats view) — it has no way for an agent to create, update, or delete an individual record. The reporter wants agents and workflows to programmatically maintain structured "records" inside a specific form, with the first concrete use case being a cross-system organization-ID mapping table for the Ginko workflow migration (NinjaOne org ID, Huntress org ID, IT Glue org ID, HaloPSA client ID, ConnectWise company name, etc.). Success means an agent can safely list/filter/paginate, fetch by ID, create, update, and delete records in a given form — with the form's own validation rules and tenant-level authorization preserved — without falling back to manual UI maintenance.

**Amendment (2026-10-15), folded in after the first design pass**: Damon Zhou added a sixth-tool requirement, `mspbots_forms_record_lookup` — read-only, with a fixed/versioned output contract — so the same Ginko mapping form can also back a Forms dropdown's `choicesSource` (an MCP-sourced, cascading dropdown mechanism he describes as already existing elsewhere in the product). He supplied a complete input/output contract verbatim in his comment; it is folded into Tech design below rather than re-derived. Separately, Jason Zhou raised a distinct risk: if a Form Event trigger watches the same form these new CRUD tools write to, an agent-originated write could re-fire that trigger and recurse. That question is **not answered by this design** — it requires a decision in the backend/trigger engine this pipeline cannot reach — and is carried forward as an Open question for groom.

## Product design

### Goals / Non-goals

Goals:
- An agent/workflow can, for a given form, list/query records with filtering and pagination, get one record by ID, create a record, update a record, and delete a record.
- Responses are structured JSON and clearly expose `form_id` and `record_id`.
- Writes enforce the form's own field validation (types, required, choices) and the same tenant-level authorization as every other tool in this MCP.
- The MVP is sufficient, end to end, for the Ginko organization-mapping first use case.
- A read-only, versioned lookup tool (`mspbots_forms_record_lookup`) can serve the same records in a flat, record-shaped form with filter/search/sort/pagination, suitable for driving a Forms dropdown's `choicesSource` (added 2026-10-15 per Damon Zhou's comment).

Non-goals:
- Does not touch, replace, or re-expose the public anonymous respondent-submission flow.
- Does not add a record-level version-history/audit UI (beyond whatever the backend already logs) unless Product asks for it separately.
- Does not add bulk import/export tooling (CSV export already exists in the Forms UI and is out of scope here).
- Does not change the Forms app front-end.
- `record_lookup` does not itself wire up any Forms dropdown — configuring a question's `choicesSource` to point at it is Forms app configuration, not something this MCP change does.
- Does not decide or implement a fix for the agent-write-triggers-event recursion risk Jason Zhou raised — that is a backend/trigger-engine decision outside this repository's reach (see Open questions, Risks).

### Acceptance criteria AC1..AC7

- **AC1**: Given an existing form ID, When an agent calls the record list/query tool with a filter (e.g. status) and a pagination limit, Then only matching records scoped to that form are returned, with a `nextCursor` enabling a further page — records from other forms or other tenants never appear.
- **AC2**: Given a known `record_id`, When an agent calls the get-by-id tool, Then the full structured field data for that record is returned, or a `not_found` error if the id doesn't exist or belongs to a different form; Given a form and valid field values, When an agent calls create/update/delete, Then the record is created/updated/deleted and a subsequent get/list reflects it — delete requires an explicit `confirm=true`, matching the existing `form_delete`/`share_delete` pattern.
- **AC3**: Given a create or get response, When it is parsed, Then it explicitly contains `form_id` and `record_id` (not just values nested anonymously) — results are structured JSON, not ad hoc string concatenation.
- **AC4**: Given a create/update request whose values violate the form's own field definition (missing required field, value outside `choices`, wrong type), When submitted, Then the request is rejected (mapped to the existing `invalid_argument` error envelope) and no partially-written record results; Given a cross-tenant call (a `record_id` that belongs to tenant B, called with tenant A's credentials), When any record tool is called with it, Then the response is `not_found` or `unauthorized` and does not reveal the record's existence or content.
- **AC5**: Given the Ginko organization-mapping field set (NinjaOne/Huntress/IT Glue/HaloPSA/ConnectWise identifiers, etc.), When an agent runs the full lifecycle (create → update one field → list to confirm → delete) using only the new tools, Then every step succeeds without falling back to manual UI maintenance.
- **AC6** *(added 2026-10-15)*: Given a form with N completed records, When a client calls `mspbots_forms_record_lookup` with a `limit` and follows `nextCursor` across pages, Then every completed record is returned exactly once in a stable order and the final `total` equals N; Given a `filter` (e.g. `status = "Active"`) and a `fields` projection, When the same tool is called, Then only matching records are returned containing only the projected fields plus the `_`-prefixed system fields, and `total` reflects the filter; Given a `search` term and `searchFields`, When called, Then only case-insensitive substring matches on those fields are returned.
- **AC7** *(added 2026-10-15)*: Given any call to `mspbots_forms_record_lookup`, Then the tool declares an `outputSchema` and its `structuredContent` always validates against it; Given an unknown `formId` or an unknown field name in `fields`/`filter`/`sort`, When called, Then a structured error (code + message) is returned, never a silently-empty list; the tool is annotated `readOnlyHint: true` and enforces the same tenant-scoped authorization as every other tool in this MCP.

### Open questions

- **[Assumed]** The real backend (`app-forms`) code is outside this pipeline's reach, and its documented contract has **no authenticated single-record read/write endpoints at all** — only list+summary (read-only) and the anonymous public-submit flow. See Tech design §3 for why. If Product considers them the same data and wants agent writes to count the same as respondent submissions, §3/§5 need rework.
- **[Not blocking]** "Ginko" has zero hits anywhere in the product fact base (wiki) — there is no way to confirm whether an existing organization-mapping form template or naming convention already exists. Proceeding on the ticket's literal wording; does not affect the tool-layer design itself.
- **[Not blocking]** The `app-forms` backend repository is not among the 79 live `Code Project` options (confirmed 2026-10-14) — this dependency cannot be progressed under this ticket alone and likely needs its own ticket against whichever repo owns that backend, or an explicit scope note at groom.
- **[Needs groom]** *(added 2026-10-15, raised by Jason Zhou)*: if a Form Event trigger is configured to fire agent/SOP execution on new submissions to the same form these CRUD tools write to, an agent-originated `record_create`/`record_update` could re-trigger that event and recurse. - **[Not blocking]** *(added 2026-10-15)*: Damon's claim that Forms dropdowns already support an MCP-sourced `choicesSource` with cascading auto-fill is unverified against wiki or any reachable repo (see Current state). This design builds `record_lookup`'s contract as specified regardless; if the consuming mechanism does not yet exist on the Forms side, wiring it up is separate work for the Forms team, not part of this ticket's scope.

## Tech design

### Conclusion

Add a new tool group to `mspbots-forms-mcp` — `mspbots_forms_record_list/get/create/update/delete` — backed by a **new, independent resource** (`/surveys/{form_id}/records`), reusing this repo's existing client/error/pagination/confirm-delete infrastructure wholesale. The MCP layer only shapes parameters and forwards them; field validation and tenant isolation stay where they already live for every other write tool — in the backend API. This is the cheapest correct option because it reuses `FormsAPIClient`, `error_envelope`, `dump_json_capped`, and the `confirm=true` safety pattern verbatim instead of inventing new plumbing. **The load-bearing precondition is that the `app-forms` backend adds these endpoints — that work is outside this repository and cannot be verified or implemented here.**

*(Added 2026-10-15)* This design also adds a **sixth, read-only tool**, `mspbots_forms_record_lookup`, whose input/output contract was specified by the requester (Damon Zhou) to back a Forms dropdown's `choicesSource`. It shares the same backend list endpoint and the same hard dependency as the five CRUD tools above — it is not a new dependency, just a new, fixed-contract consumer of the same planned `GET /surveys/{form_id}/records` endpoint.

### Where the current implementation lives

- `src/mspbots_forms_mcp/tools/forms.py:32-145` — pagination (`cursor`/`limit` clamp to 100) and DSL-validation pattern for list/get/create; the new record tools should mirror this shape.
- `src/mspbots_forms_mcp/tools/forms.py:242-277` — `form_delete`'s `confirm=true` safety gate; `record_delete` should reuse the identical convention.
- `src/mspbots_forms_mcp/tools/responses.py:46-84` — `response_list`'s existing `status`/`share_id`/`cursor`/`limit` filter and pagination shape; `record_list` should match it for consistency (same clamp of 100, same cursor semantics).
- `src/mspbots_forms_mcp/api_client.py:98-192` — `FormsAPIClient` already wraps GET/POST/PATCH/DELETE with retry and the tenant cookie; record tools call it directly, no new client code needed.
- `src/mspbots_forms_mcp/_json.py:76-77` and `src/mspbots_forms_mcp/tools/_common.py:1-7` — `error_envelope` and `NO_TOKEN` are reused as-is.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Extend the existing `/responses` resource with POST/PATCH/DELETE | Reuse `response_id`, add write methods on the same resource | Smallest surface, path reuse | Conflates respondent-facing analytics with agent-maintained structured data — agent writes would pollute `totalStarted`/`completionRate` meant for real respondents, and directly contradicts the README's stated safety principle that an agent must not act as a respondent | Rejected |
| B. New, independent `/records` resource alongside `/responses` | New path `/surveys/{id}/records`; backend decides storage (new table, or same table tagged `source=agent`) | Clean semantics; keeps respondent analytics untouched; future audit can distinguish agent-written vs respondent-submitted data | Requires the backend to build a genuinely new endpoint group — a cross-repo dependency this repo's own change cannot satisfy alone | **Selected** |

No other option is natural here — this gap cannot be closed by front-end or MCP-layer tricks alone; it requires new backend surface regardless of which option is chosen.

### Data & API contract

(Assumed, pending backend confirmation — see Open questions / Risks.)

- `GET /apps/app-forms/api/surveys/{form_id}/records?status=&cursor=&limit=` → `{"items": [{"id": str, "formId": str, "status": str, "createdAt": str, "updatedAt": str, "fields": {<question name>: <value>}}], "nextCursor": str|null}`. Unlike `response_list`'s columnar shape, records use a `fields` object keyed by question name — records are consumed programmatically, not rendered for a human, so the columnar token-saving trick response_list uses doesn't apply here.
- `GET /apps/app-forms/api/surveys/{form_id}/records/{record_id}` → the same single-object shape; 404 → `{"error": {"code": "not_found", ...}}`.
- `POST /apps/app-forms/api/surveys/{form_id}/records` body `{"fields": {...}}` → 201 + the new record; field-validation failure → 422 (mapped to the existing `invalid_argument` envelope).
- `PATCH /apps/app-forms/api/surveys/{form_id}/records/{record_id}` body `{"fields": {...}}` — whether this is a partial merge or a full replace is a contract detail the backend team needs to confirm; this design recommends partial (matching the "shallow merge" precedent `form_update`'s `definition` field already uses), but it isn't settled.
- `DELETE /apps/app-forms/api/surveys/{form_id}/records/{record_id}` → 204; the MCP tool only forwards this when `confirm=true`.
- Backward compatibility: this is an entirely new resource — no existing endpoint or tool is touched, no migration needed.
- **`mspbots_forms_record_lookup`** *(read-only; added 2026-10-15 — contract as specified verbatim by the requester, Damon Zhou; shares the planned `GET /surveys/{form_id}/records` list endpoint above, does not require a separate backend endpoint)*:
  - Input: `formId` (string, required); `fields` (string[], optional projection by question name, default = all answer fields); `filter` (`{field, op, value}[]`, optional, ops at least `eq/ne/in/contains/startsWith/isEmpty/notEmpty`, AND semantics, **applied server-side before paging** so total/paging stay correct); `search` (string, optional type-ahead); `searchFields` (string[], optional, default = `fields`); `sort` (`{by, dir}[]`, optional, default `submittedAt desc` then record-id tie-break for stable order); `limit` (int, optional, default 100, max 1000); `cursor` (opaque, optional).
  - Output (`structuredContent`, with a declared `outputSchema`): `{"formId": str, "records": [{"_recordId": str, "_submittedAt": str, "_updatedAt": str, "<question name>": <value>, ...}], "nextCursor": str|null, "total": int}`. Keys are question names (not titles); system fields are `_`-prefixed so they never collide with a question literally named e.g. `recordId`. Values: dropdown/radio = stored value not display text; multi-select/tagbox = array; empty = `null`; numbers/booleans keep their JSON type; textarea keeps newlines. Only current, completed records — excludes in-progress/draft/deleted; edited records return the latest version only (one row per record).
  - Determinism/caching: the requester caches by args hash for ~60s client-side, so identical inputs must produce identical output — this constrains the backend's tie-break ordering more than it constrains this MCP's own (stateless) implementation.
  - Performance target (requester-specified, not independently verified here): < 1s for a 5,000-record form with filter + projection; Forms is expected to cap at 5,000 records / 50 pages per dropdown.
  - Errors: an unknown `formId`, or an unknown field name anywhere in `fields`/`filter`/`sort`, → a structured error (code + message) — **never** a silently-empty list.
  - `readOnlyHint: true`; no side effects; same tenant-scoped authorization as every other tool in this MCP.
  - How Forms is expected to consume it (per the requester, no Forms-repo change implied by this ticket): `choicesSource = {type: "mcp", toolName: "mspbots_forms_record_lookup", args: {formId, fields, filter}, responsePath: "records", valueField: "<question>", displayField: "<question>", paging: {cursorArg: "cursor", nextCursorPath: "nextCursor"}, search: {arg: "search"}}`.

### Key flow / sequence

Agent → `mspbots_forms_record_create(form_id, fields)` → `FormsAPIClient.post("/surveys/{id}/records", {fields})` → backend validates `fields` against the form's question definition → `201 {record}` → MCP returns `dump_json_capped(record)`.
Failure path: invalid field value → `422` → `FormsAPIError` → `error_envelope("invalid_argument", ...)` → the agent sees a structured error instead of a raw exception.

### Non-functional

- **Idempotency / concurrency**: `create` is non-idempotent by nature (each call makes a new record); `update`/`delete` are idempotent with respect to the target record's end state, consistent with `form_update`'s `idempotentHint`. Whether concurrent updates to the same record need conflict detection (an `If-Match`/version field) is left to the backend contract — flagged as an open contract detail, not resolved here.
- **Performance**: reuse `response_list`'s existing `limit` clamp (100) and cursor pagination rather than ever returning an unbounded page. The Ginko use case implies record counts at "number of organizations" scale (well under 10^4) — no additional indexing design is needed at this scope.
- **Security**: auth points are identical to every existing tool (`X-API-Key` + the `X-MSP-Tenant-Id` → `X_Tenant_ID` cookie, enforced by the app-routing gateway plus backend business logic). Field values may contain customer PSA/ticketing identifiers — tenant data, not credentials, but logs should not print full `fields` payloads, matching the existing response tools' practice of never logging individual cell values.
- **Multi-tenant isolation**: this is the core of the AC4 cross-tenant test case. Record-ownership checks must happen in the backend; the MCP layer does not and structurally cannot perform a second check (it never holds another tenant's credentials).
- **Observability**: reuse `FormsAPIError.to_envelope()` as-is so every error carries a `retryable` flag the agent can act on; no new logging infrastructure is needed.
- **Caching determinism** *(added 2026-10-15)*: `record_lookup` is specified by the requester to be deterministic for identical inputs, because Forms is expected to cache its output by args hash for ~60s client-side. This mainly constrains the backend's tie-break ordering (stable `submittedAt desc` + record-id tie-break); this MCP's own implementation stays stateless and adds no cache of its own.

### Rollout & rollback

No feature-flag mechanism exists in this repo (it's a stateless MCP — tools take effect as soon as the server restarts with the new code). Per the repo's existing discipline, write paths should be verified against a disposable test form (INT, never PROD) before merging. Rollback is a plain revert of the commit / removing the 6 tools from `server.py`'s register list; the existing 14 tools are unaffected either way. **The real rollout order is: backend ships the new endpoints first, then this repo ships the tools** — shipping the tools first means every call 404s or returns `upstream_error`. `record_lookup` ships alongside the 5 CRUD tools in the same rollout — it has no independent rollout path since it depends on the same backend list endpoint.

### Test strategy

Unit (this repo, mocked `httpx`, no real network): tool-list snapshot update, record CRUD parameter shaping, 404/422/confirm-rejection paths, cursor pass-through, and for `record_lookup`: pagination/total exactness, filter+projection, search, unknown-`formId`/unknown-field structured errors, `outputSchema` validation.
Integration / manual: once the backend endpoints exist, run create→get→update→list→delete end to end against a disposable test form (never a real PROD form with real data — matching the README's existing write-tool testing discipline). A separate manual check verifies a Forms dropdown configured with `choicesSource` against `record_lookup` loads and cascades, if/when the Forms side is wired up — flagged as untested here since that wiring is outside this repository (see Test cases TC15).
