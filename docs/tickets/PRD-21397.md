# PRD-21397 · [Feature] Export/import MSPbots Forms across tenants

Ticket: https://app.clickup.com/t/2280862/PRD-21397
Repo: https://github.com/MSPbotsAIFramework/mspbots-forms-mcp@main (35c6ccf)
Work branch: dev/PRD-21397
Status: frozen @ f0d612b

## Requirement understanding

One line: A form built and tested in one tenant can be copied into another tenant's Forms exactly, without hand-rebuilding it, by exporting it to a file and importing that file into the destination tenant.

Don (reporter) needs a tested MSPbots form (first case: PRECICOM's offboarding form) to exist identically in a client tenant without manual recreation, which today risks drift between the tested and the live form. Micus (Backlog BA) finalized the v1 scope on 2026-10-26: file-based export/import only (no direct tenant-to-tenant copy), workspace-admins-only, and data-source-bound fields imported unbound with a report so the admin can reconnect them. Success is a field-by-field identical definition (IDs aside), matching settings (including "requires Microsoft 365 sign-in"), and zero copied responses.

## Current state

MSPbots Forms (product name "Forms", backend wire name "survey") is reached through the `mspbots-forms-mcp` MCP server, which wraps an internal MSPbots App API (`/apps/app-forms/api/...`) — this is explicitly not a third-party vendor connector (`README.md:3-4`). The server exposes 14 tools across three groups: Form, Share, Response (`src/mspbots_forms_mcp/server.py:104-130`, `tests/test_tools.py:18-31` pins the exact set of 14).

Relevant existing primitives, all read:

- `mspbots_forms_form_get(form_id, include=["definition", "questions", "versions"])` → `GET /surveys/{form_id}` — `include=["definition"]` returns the full raw SurveyJS-shaped JSON (`src/mspbots_forms_mcp/tools/forms.py:59-87`).
- `mspbots_forms_form_create(title, questions, pages, show_progress_bar)` → `POST /surveys` — creates a new **draft, unpublished** form from the friendly question DSL (`forms.py:89-145`).
- `mspbots_forms_form_update(form_id, title, show_progress_bar, questions, pages, definition)` → `PATCH /surveys/{form_id}` — the `definition` param already accepts **raw SurveyJS JSON** "for edits not expressible via the DSL... e.g. custom validators or choicesByUrl" (`forms.py:178-222`, docstring literally names `choicesByUrl` as the data-source mechanism — this is the strongest piece of in-repo evidence for how API-driven dropdowns are represented).
- `mspbots_forms_form_publish`, `mspbots_forms_form_delete` — not relevant to this feature; imported forms must stay unpublished per the requirement.

No export, import, duplicate, or template tool exists today (`forms.py` has exactly the 7 tools above, none named export/import/duplicate/template). `wiki: ProductDocs/Apps/forms/00-Index.md` confirms the same from the UI side: "Export CSV" in the live app is a responses download, not a form-definition export, and it is explicitly out of patrol scope; no duplicate/template feature is documented anywhere in `ProductDocs/Apps/forms/**` (_verified_ 2026-08-17, app v0.0.9). So this is new capability, not a bug in an existing one.

Per-request tenant isolation (load-bearing for this design): every MCP call carries exactly one tenant's credentials — `X-API-Key`, `X-MSP-Host`, `X-MSP-Tenant-Id` headers, stored in a per-request `contextvar` and forwarded downstream as an `X_Tenant_ID` **cookie** (`server.py:17-28, 61-96`; `api_client.py:79-91` explains why it must be a cookie, not a header — the APISIX app-routing gateway in front of the Forms API 404s without it). There is **no mechanism in this server for one request to hold two tenants' credentials at once.** This means cross-tenant transfer cannot be a single tool call; it has to be two separate tool calls (export under the source tenant's connector binding, import under the destination tenant's), with the human/agent carrying the JSON payload between them — which matches the requirement's own description of the workflow ("MSPbots staff using Switch Tenant").

The MCP server has no notion of caller *role* within a tenant — the three headers identify the tenant and an access credential, not a user or a role (`server.py:61-90`). "Workspace admins only" (requirement scope item (b)) is therefore not something this server can check; see Tech design §7 and Open questions.

`wiki` does not cover: the JSON location/shape of the "requires Microsoft 365 sign-in" form setting, or any "workspace admin" role concept for Forms (`wiki find "workspace admin"` → no hits). Both are treated as assumptions below (Open questions), not blocking.

## Product design

### Goals / Non-goals

Goals:
- Export a form's full definition (fields, options, order, sections/pages, conditional logic, validation, and form-level settings) to a single JSON file.
- Import that file into another tenant, creating a new unpublished form with a new ID, named `"{original title} (imported)"`.
- Flag, not silently copy, anything that is tenant-specific: data-source-bound fields and static options carrying tenant identifiers. List them in a short report after import so the admin can reconnect them.
- Refuse a file from a newer/unknown export version outright, with a clear message — never a half-import.

Non-goals (v1, per Micus's decision 2026-10-26):
- Direct tenant-to-tenant copy without a file.
- Copying submitted responses, the original form ID, owners/sharing, or trigger links.
- Automatically re-pointing the client agent's trigger to the new form ID (admin does this by hand).
- Form templates / a shared template library.
- Copying agents.

### Acceptance criteria

- **AC1** (field-for-field fidelity): Given a form F with no data-source-bound fields, When it is exported and the file is imported into another tenant, Then the imported form's definition — every field's type, label, description, placeholder, options, required flag, default value, order, and page/section structure, plus conditional/cascading logic and validation — is identical to F's, except for IDs (the new form has a new form ID; internal question names such as `q1`/`q2` are preserved as-is since they are part of the copied definition).
- **AC2** (settings fidelity): Given F has form-level settings including "requires Microsoft 365 sign-in", progress bar, and thank-you message, When exported and imported, Then every one of those settings is identical on the imported form.
- **AC3** (no responses): Given F has zero or more submitted responses, When F is imported, Then the imported form has zero responses, regardless of how many the source had.
- **AC4** (data-source fields flagged): Given F has a question whose choices come from a data source (`choicesByUrl`, i.e. an API-driven/MCP-data-fetch dropdown), When F is imported, Then the imported question is unbound (no working `choicesByUrl`) and that question appears in the import report.
- **AC5** (tenant-scoped static options flagged): Given F has a question with static choice options carrying tenant-scoped identifiers (the pattern named in the ticket: keys such as `tenantId`, `haloClientId`, `rewstOrgId` — e.g. the `client_org` options on Ginko's form), When F is imported, Then those tenant-specific option values do not survive into the destination tenant's form unbound-and-flagged the same way as AC4, and the question appears in the import report.
- **AC6** (version refusal): Given an export file whose format/version the importing server does not recognize (newer than what it supports, or unrecognized), When import is attempted, Then the server refuses with a clear, specific error (naming the unsupported version) and creates no form — not a partial import.
- **AC7** (actionable result): Given import succeeds, Then the response includes the new form's ID (so the admin can point the client agent's trigger at it) and the import report (empty list when nothing was flagged).
- **AC8** (cross-tenant isolation): Given an export produced under tenant A's credentials, When the file is imported under tenant B's credentials, Then no call made during import uses tenant A's credentials or tenant ID (the existing per-request, single-tenant isolation in `server.py` is not weakened by this feature), and no tenant-A-scoped identifier from AC5 survives into tenant B's form un-flagged.

### Open questions

- [assumed, non-blocking] The exact in-repo location of "requires Microsoft 365 sign-in" within the full form record/definition is not verified here (the API contract this server was built from is itself marked unverified, `forms.py:1-12`). **Assumption**: export carries the entire record returned by `form_get(include=["definition"])` (plus base fields) verbatim, so whichever field holds this setting travels automatically — the design does not depend on enumerating every settings field by name. If that assumption is wrong (the setting lives in a call this export doesn't make), AC2 needs revisiting.
- [assumed, non-blocking] "Workspace admins only" (scope item (b)) cannot be enforced inside this MCP server — it has no caller-role information, only tenant + a bearer credential (Current state, above). **Assumption**: this is enforced the same way other sensitive tools in this fleet are — by only granting the export/import tools to an admin-scoped connector binding at the Agent Platform layer, outside this repo. This design does not add an in-server role check. If platform-side enforcement doesn't exist yet, that's a platform-team follow-up, not a blocker for shipping these two tools.
- [non-blocking] The set of "tenant-scoped" static-option keys (AC5) starts as exactly the three named in the ticket (`tenantId`, `haloClientId`, `rewstOrgId`). Extending it to other integrations' tenant-id-shaped keys is a follow-up, done by editing one constant (Tech design §4).
- [non-blocking] Re-importing the same file twice creates two separate forms (no de-duplication) — the requirement doesn't ask for idempotency here, so none is added.

## Tech design

### Conclusion

Add two new MCP tools, `mspbots_forms_form_export` and `mspbots_forms_form_import`, to the existing `mspbots-forms-mcp` server — no backend API changes, no new REST endpoints. Export composes the existing read tool (`form_get` with `include=["definition"]`) into a versioned envelope. Import validates the envelope version, walks the definition tree generically (not assuming a fixed SurveyJS shape, since that shape is itself unverified in this repo) to strip/flag data-source- and tenant-id-bound choices, then composes the existing write tools (`form_create` for a titled shell, `form_update` with the stripped `definition`) to materialize the new form in the destination tenant. Both tools are pure composition of existing, already-tenant-isolated primitives — the per-request credential model in `server.py` is untouched.

### Where the current implementation lives

- `src/mspbots_forms_mcp/tools/forms.py` — the module to extend; `register()` at `forms.py:30` is where new `@mcp.tool()` functions get added, following the exact style of the 7 tools already there.
- `src/mspbots_forms_mcp/api_client.py` — `FormsAPIClient` (`api_client.py:73-191`) already exposes `get`/`post`/`patch`/`delete`; no change needed, the new tools call `client.get`/`client.post`/`client.patch` exactly like existing tools do.
- `src/mspbots_forms_mcp/_json.py` — `dump_json_capped`, `error_envelope` (used by every existing tool for output shaping and error responses; reused as-is).
- `src/mspbots_forms_mcp/server.py:99-140` — `create_mcp_server` wires `forms.register(mcp, client_factory)`; no change needed beyond whatever `forms.py` exports growing by two tools.
- `tests/test_tools.py:18-31` — `EXPECTED_TOOLS` is an explicit snapshot of all tool names/signatures/annotations, asserted against `len(tools) == 14`. This test **must** be updated (two new entries, count → 16) as part of this change, or the gate fails by design (the comment at `test_tools.py:16-17` calls this out as a deliberate breaking-change tripwire).

### Data & API contract

New MCP tool: `mspbots_forms_form_export`

- Input: `form_id: str` (required).
- Behavior: `GET /surveys/{form_id}?include=definition,questions,versions` (reuses the exact params shape `form_get` already builds, `forms.py:82`).
- Output (JSON, via `dump_json_capped`):
  ```json
  {
    "export_version": 1,
    "exported_at": "2026-10-27T14:00:00Z",
    "source_form_id": "9030b62e-4000-4e61-ae98-2b7285c86ea6",
    "form": { "...": "the full record returned by GET /surveys/{form_id}?include=definition,questions,versions, verbatim" }
  }
  ```
  `form` is deliberately the raw upstream response, not a re-shaped subset — this is what makes AC1/AC2 ("identical except IDs") achievable without needing to enumerate every settings field by name (Open questions).
- Errors: passes through `FormsAPIError.to_envelope()` unchanged (404 if `form_id` doesn't exist, etc.) — identical error behavior to `form_get`.

New MCP tool: `mspbots_forms_form_import`

- Input: `export_payload: dict` (required — the object produced by `form_export`, or an equivalent hand-built one), `title_suffix: str` (optional, default `" (imported)"`, for the "(imported)" naming rule — exposed as a parameter rather than hardcoded so a re-import after a naming collision can use a different suffix without code changes).
- Behavior:
  1. `validate_export_version(export_payload)` — raises before any network call if `export_version` is missing or not `1`.
  2. Extract `title = export_payload["form"]["title"]`, `definition = export_payload["form"]["definition"]`.
  3. `stripped_definition, report = strip_tenant_specific(definition)`.
  4. `created = await client.post("/surveys", {"title": f"{title}{title_suffix}"})` → `new_form_id = created["id"]`.
  5. `await client.patch(f"/surveys/{new_form_id}", {"definition": stripped_definition, "title": f"{title}{title_suffix}"})`.
  6. Return `{"form_id": new_form_id, "title": f"{title}{title_suffix}", "report": report}`.
- Output (JSON):
  ```json
  {
    "form_id": "a1b2c3d4-...",
    "title": "PRECICOM offboarding (imported)",
    "report": [
      {"field": "client_org", "reason": "static tenant-scoped options (tenantId, haloClientId, rewstOrgId)"}
    ]
  }
  ```
- Errors: unsupported version → `error_envelope("invalid_argument", "Unsupported export_version: <got>. This server supports: 1.", retryable=False)`, no `post`/`patch` call made. Upstream `FormsAPIError` during step 4 or 5 → passed through via `to_envelope()`; if step 5 fails after step 4 succeeded, the shell form already exists in draft — same accepted non-atomicity as `form_quick_publish` (§9 test strategy covers this explicitly so it's a documented gap, not a silent one).
- Backward compatibility: `export_version` is the only versioning surface; a future `export_version: 2` (e.g. carrying share/theme settings) requires both a new `strip_tenant_specific` code path and a version-dispatch in `form_import` — nothing in this change prevents that.

### Key flow / sequence

```
Admin (tenant A context)                Admin (tenant B context)
  |                                        |
  |--mspbots_forms_form_export(form_id)--->|
  |   GET /surveys/{id}?include=...        |
  |<--{export_version, form:{...}}---------|
  |                                        |
  |   [admin carries the JSON file         |
  |    across tenants, e.g. Switch Tenant] |
  |                                        |
  |                                        |--mspbots_forms_form_import(payload)-->
  |                                        |   validate_export_version
  |                                        |   strip_tenant_specific(definition)
  |                                        |   POST /surveys {title}         -> new_id
  |                                        |   PATCH /surveys/{new_id} {def} -> ok
  |                                        |<--{form_id, title, report}-----------
```

Both tool calls are independent MCP requests, each carrying only one tenant's credentials (`X-API-Key`/`X-MSP-Host`/`X-MSP-Tenant-Id`) — there is no step where this server holds tenant A's and tenant B's credentials at the same time.

### Non-functional

- **Idempotency & concurrency**: `form_export` is read-only, safe to call repeatedly and concurrently. `form_import` is **not** idempotent — each call creates a new form with a new ID (Open questions: no de-dup requested). No shared mutable state in this server (`api_client.py:20-25`'s connection pool is already documented as credential-free and request-scoped), so concurrent imports into the same or different tenants don't interfere with each other beyond whatever the backend itself serializes.
- **Performance**: form definitions are "several KB" per the existing `form_get` docstring (`forms.py:76-78`) — export/import is a single small-payload round trip each, no pagination, no batching needed. No new hot path.
- **Security**: tenant isolation is preserved by construction (Key flow, above) — this feature adds no new cross-tenant data path, since each tool call stays inside the existing single-tenant-per-request model. "Workspace admins only" is **not enforceable inside this server** (Current state) — flagged as an assumption in Open questions, not implemented here. The export payload is plain JSON (not encrypted) — same trust level as any other data this MCP already returns to the calling agent/platform; no new secret material is introduced (the payload contains form structure, not credentials).
- **Multi-tenant isolation**: `strip_tenant_specific` is the mechanism that prevents a literal tenant A identifier (e.g. a `haloClientId` baked into a static choice option) from silently becoming "live" data in tenant B's form — this is the concrete, testable form of AC5/AC8, and is covered by unit tests independent of any real tenant.
- **Observability**: no logging framework exists elsewhere in this repo to extend (consistent with the rest of the codebase — errors surface via the returned `error_envelope`, not server-side logs). Nothing added here changes that.

### Rollout & rollback

- Purely additive: two new tool registrations plus one new helper module. No change to any existing tool's signature or behavior, no schema/migration. Safe to ship directly.
- Rollout order (single repo, matches §3 of `references/mcp-track.md`): implement → gates (`uv run pytest`, `initialize`/`tools/list` smoke, no-Chinese scan, README Connector-section check) → merge to `main` → `mcppub publish` to INT.
- Rollback: revert the merge commit (`git revert`) — no data was written anywhere outside individual imported forms a user explicitly created by calling the tool, so there is nothing to clean up structurally; a bad release simply removes the two tools again.

### Test strategy

- **Unit (no network)**: `tests/test_transfer.py` — `strip_tenant_specific` against hand-built definition fixtures covering: a plain field (untouched), a `choicesByUrl` field (stripped + reported), a static-choices field carrying `tenantId`/`haloClientId`/`rewstOrgId` (stripped + reported), a field with ordinary string choices sharing no tenant-shaped keys (untouched — must not over-strip), and a definition nested inside pages/panels (recursion reaches it). `validate_export_version` against version `1` (passes), missing version, and version `2` (both raise with the expected message).
- **Tool-registration regression**: `tests/test_tools.py::test_tools_list_snapshot` extended to 16 tools — this is the existing contract tripwire (§ Change list), not new infrastructure.
- **Manual / INT**: the full round trip against a real deployment — export a real form (ideally structured like PRECICOM's offboarding form) from one INT tenant, import into another, diff the two definitions. This is the only way to validate AC1/AC2 against the real, still partly-unverified backend contract (`forms.py:1-12` — write tools here have historically been "deliberately not exercised against PROD without explicit sign-off"; INT is the safe environment per `README.md:84`).
- **Regression surface**: none of the 14 existing tools change behavior; the only shared surface is `server.py`'s tool-registration wiring and the `EXPECTED_TOOLS` snapshot test, both exercised by the existing test suite.

### Effort & breakdown

Rough order of magnitude: **0.5–1.5 person-days** — the bulk of the uncertainty is in the INT round-trip verification (depends on getting a real multi-tenant test form and a second tenant to import into), not the code itself (two tools composing four already-existing API calls, plus one pure-function helper).

Suggested sub-tasks (each independently verifiable):
1. `strip_tenant_specific` + `validate_export_version` + unit tests (no network).
2. `mspbots_forms_form_export` tool + wiring + `EXPECTED_TOOLS`/README updates.
3. `mspbots_forms_form_import` tool (depends on 1 and the shape produced by 2).
4. INT round-trip manual verification (depends on 2 and 3 both being deployed, or run locally against INT per `README.md`'s Quick Start).

### Risks & dependencies

- **Unverified backend contract**: this entire MCP server was built from a pasted API contract, not the backend source (`forms.py:1-12`, README "Known Gaps"). The biggest risk is that `GET /surveys/{id}?include=definition` does not actually return a definition that can be posted back byte-for-byte via `PATCH .../definition` — i.e., that round-tripping through this server's own existing tools isn't actually lossless today, independent of anything this ticket adds (this risk exists in the current code regardless of this ticket). Mitigated by the INT manual test in §9, not by code review alone.
- **Settings fidelity depends on an unverified field shape** (Open questions) — if "requires Microsoft 365 sign-in" turns out to live somewhere the `include=definition,questions,versions` call doesn't reach, AC2 silently fails; the INT round-trip test is the catch for this.
- **No dependency on other tickets.** `PRD-21379` (Forms MCP truncates option properties) and `PRD-21470` (Forms clear GDAP values on submit) touch the same repo/file area (`forms.py`) but are independent bugs, not blockers — worth a quick rebase check at dev time since they may land on `main` concurrently.
- **Platform-side admin-only enforcement** (Open questions) is a dependency this ticket cannot resolve from within this repo; flagged, not blocking.

## Test cases

Full steps, preconditions and evidence fields live in the sibling `docs/tickets/PRD-21397.ac.json`; this section carries only the pass/fail statements per AC.

- **TC1 · AC1** (auto): Given a definition with ordinary fields across two pages and no data-source/tenant-scoped choices, When exported then imported, Then the imported definition equals the source definition except for the (new) form ID.
- **TC2 · AC2** (manual, INT): Given a real form with "requires Microsoft 365 sign-in" enabled plus non-default progress-bar/thank-you-message settings, When exported then imported on INT, Then all three settings match on the imported form.
- **TC3 · AC3** (manual, INT): Given a real form with at least one submitted response, When imported, Then the imported form has 0 responses.
- **TC4 · AC4** (auto): Given a definition with one question using `choicesByUrl`, When `strip_tenant_specific` runs, Then that question has no `choicesByUrl` and no `choices`, and the report lists it with reason "data-source-bound".
- **TC5 · AC5** (auto): Given a definition with a `client_org`-style question whose static choices are objects carrying `tenantId`/`haloClientId`/`rewstOrgId`, When `strip_tenant_specific` runs, Then `choices` is cleared and the report lists the question with the matched key names.
- **TC6 · AC5 (negative)** (auto): Given a definition with an ordinary question whose static choices are plain strings (no tenant-shaped keys), When `strip_tenant_specific` runs, Then the question is returned unchanged and does not appear in the report (guards against over-stripping).

### Over-stripping guard (why TC6 matters)

`strip_tenant_specific` only clears `choices` when at least one choice item is a `dict` containing a key in `TENANT_SCOPED_CHOICE_KEYS`. Plain string choices (`["Red", "Green", "Blue"]`) never match `isinstance(choice, dict)`, so TC6's ordinary question survives untouched — this is the concrete guard against over-stripping called out in the Tech design's "Unit (no network)" test strategy.
