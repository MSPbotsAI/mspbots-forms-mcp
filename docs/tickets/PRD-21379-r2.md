**Evidence the requirement itself is unchanged**: the ticket description (`text_content`) is identical to
what round 1's "Requirement understanding" section already restates — the reporter still wants

that the shipped fix does not deliver the behavior round 1's own AC1/AC2 already committed to.

**Root cause, verified against the current code** (`src/mspbots_forms_mcp/tools/forms.py:118-126`,
`src/mspbots_forms_mcp/_json.py:18-61`, read at `dev01.mbagent/PRD-21379 @ 104e1a3`):

- `mspbots_forms_form_get` with `field_id` set returns `dump_json_capped({"form_id": ..., "field_id": ...,
  **question})` — the matched SurveyJS element's own keys spread at the top level (as round 1's tech design
  required, to let `dump_json_capped`'s top-level-list truncation reach an oversized choice list).
- Round 1's tech design and its test mocks (`tests/test_tools.py:126-151`, `_client_org_definition`) both
  assumed the question element carries its options as a flat top-level `"choices": [...]` list.
- The real `client_org` question on form `f7528a78` v4 does not have that shape. Per Tom's `[TEST]` comment,
  the real element carries `choicesSource: {items: [...185 entries...], passAttributes: ["rewstOrgId",
  "haloClientId", "tenantId"]}` — a SurveyJS *static choice source* reference, which is a **dict**, not a
  list.
- `dump_json_capped` (`_json.py:28-30`) only looks for **top-level dict keys whose value is a list**
  (`list_keys = [k for k, v in data.items() if isinstance(v, list)]`). Because `choicesSource` is a dict, it
  is invisible to that scan. The spread question dict (`form_id`, `field_id`, `name`, `type`, `title`,
  `isRequired`, `choicesSource`) has **no top-level list field at all**, so the function falls straight to
  the final branch (`_json.py:54-61`) and the entire 51,122-char payload collapses to a 116-char
  `"truncated": true, "note": "Result too large ... not list-shaped"` notice — 0 of 185 options returned,
  exactly as Tom reproduced.
- `find_question_by_name` (`src/mspbots_forms_mcp/tools/_survey_walk.py`) itself is shape-agnostic — it
  returns whatever element dict it finds and is not implicated. The gap is entirely in (a) the response-shape
  assumption baked into round 1's tech design / `forms.py` spread logic, and (b) the test mocks, which
  exercised only the assumed `choices: [...]` shape and therefore could not have caught this — this matches
  "开发错误" judging criterion 2 (AC1/AC2 intended to cover this, but the test suite's only path to the real
  shape, TC5, was recorded `untested` in round 1 rather than run).

## Product design (amendments only — AC1-AC4, AC6 and all goals/non-goals from round 1 stand unchanged)

### Acceptance criteria — AC5 amended, AC7 added

- **AC5 (amended)** *(manual — live verification, cannot be exercised from this sandbox)*: Given the real
  offboarding form `f7528a78` v4 in the MSPbots demo tenant, When an operator with PROD/INT access calls the
  shipped `mspbots_forms_form_get` for the `client_org` question, Then the live response contains every real
  `client_org` option (all 185), and **each option retains whichever of `tenantId`, `haloClientId`, and
  `rewstOrgId` are actually present for that option in the source definition** — an option that genuinely has
  no value for one of those attributes in the source data is not required to carry it. The response must not
  silently drop the option list (0 of 185 is a fail regardless of how many options legitimately lack
  `tenantId`).
  - *Why amended*: round 1's wording ("every option ... with real tenantId ... intact") is unfalsifiable
    against the real data — 37/185 options have no `tenantId` in the source, confirmed by Tom's live test.
    The reporter's actual need (tenant-to-client mapping data is not silently dropped) is preserved; only the
    unachievable "always non-empty" clause is removed.
- **AC7 (new, regression)**: Given the `client_org` question's choices are defined via `choicesSource` (a
  SurveyJS static choice source: `{items: [...], passAttributes: [...]}`, where the option list is nested
  under a dict key rather than being a top-level list) with a realistic option count (185, matching the real
  form), When the `field_id`-filtered call is made, Then the response is well-formed JSON carrying every
  option's present `passAttributes` values — gracefully truncated per AC2 if still oversized — and must never
  collapse to the generic "Result too large ... not list-shaped" notice that discards the option list
  entirely.

### Open questions (new, this rework)

- **[not blocking this ticket]** The *unfiltered* whole-form call hits the same "not list-shaped, discard
  everything" collapse for any oversized, non-list-shaped payload (Tom's `[TEST]` comment, evidenced against
  `include=definition` with no `field_id`). This affects every caller of `mspbots_forms_form_get`, not only
  the `field_id` path this ticket owns, and round 1 explicitly scoped that path as unchanged (Non-goals,
  AC4). Recommend a follow-up ticket against `_json.py`'s `dump_json_capped` (e.g. recursing into nested dict
  values, or budgeting before serialization) rather than folding it into this one.

## Test cases (amendment — TC1-TC4, TC6 unchanged; TC5 wording aligned to amended AC5; TC7 new)

- **TC5 (AC5, manual, wording aligned to amended AC5)**: Given the real offboarding form `f7528a78` v4 in the
  MSPbots demo tenant, when an operator with PROD/INT MCP access calls the shipped
  `mspbots_forms_form_get(form_id="f7528a78", field_id="client_org")`, then the response contains all 185
  `client_org` options, and each option retains whichever of `tenantId`, `haloClientId`, `rewstOrgId` are
  present for it in the source data (no requirement that every option carry a non-empty `tenantId`); the
  response is not collapsed to a truncation notice.
- **TC7 (AC7, auto, regression — source: dev feedback comment `90170266253375`)**: Given a mocked question
  shaped like the real `client_org` question — `choicesSource: {items: [...185 entries, 37 of them missing
  tenantId...], passAttributes: ["rewstOrgId", "haloClientId", "tenantId"]}`, not a top-level `choices` list —
  when `mspbots_forms_form_get(form_id, field_id="client_org")` is called, then the response is valid JSON
  containing all (or, if still oversized, gracefully truncated per AC2) options with their present
  attributes, and the response is never the generic "Result too large ... not list-shaped" notice.
