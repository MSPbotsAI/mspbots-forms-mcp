# PRD-21379 · [Bug] Forms MCP truncates option properties

Ticket: https://app.clickup.com/t/86e3v7wzd
Repo: https://github.com/MSPbotsAI/mspbots-forms-mcp@main (4066e70)
Work branch: dev01.mbagent/PRD-21379
Status: in progress

## Requirement understanding

One line: The reporter wants `mspbots_forms_form_get` to return the full or a filtered client_org question for the offboarding form f7528a78 (41 questions) with every option's tenantId, haloClientId, and rewstOrgId properties retained, instead of a truncated response that drops them.

Today, calling `mspbots_forms_form_get` for this 41-question form returns a response that is missing the `client_org` question's per-option properties needed to map a client to its tenant. Without those properties, SOP 230's R-07 flow (prefill the offboarding form from a client email) cannot resolve the leaver's tenant and forward target, so the agent leaves those fields blank. A manual mapping in the skill configuration is being used as a workaround. Micus Zheng handed the ticket to dev01 on 2026-10-23 with priority `high` (not `urgent`, because the workaround exists), flagging it as a blocker for the Ginko SOP 230 offboarding milestone (Tier 1, due Nov 7).

- `src/mspbots_forms_mcp/_json.py:11,18-61` — `dump_json_capped` enforces a hard `MAX_CHARS = 20_000` budget (line 11) on every tool's JSON output (the module docstring at lines 1-6 explains this exists so a single tool call "can never blow past the ~20,000-char budget an agent's context can reasonably absorb"). When the serialized payload exceeds that budget, the function:
  - only looks at **top-level** `dict` keys whose value is itself a `list` (`list_keys = [...]`, line 31) — a nested list several levels inside a dict value (e.g. `pages[].elements[].choices`) is invisible to it;
  - if such a top-level list exists, it binary-searches the largest prefix of that list that fits under the budget and drops the rest from the tail (lines 35-52) — whole items are dropped, not fields within an item;
  - if no top-level list exists and the payload is still oversized, it discards the entire payload and returns a generic `"Result too large"` notice (lines 54-61).
  For a form with 41 questions requested via `include=["definition"]`, the full SurveyJS definition for a form this size is a realistic candidate to exceed 20,000 chars; depending on exactly where in the (not independently verified, see below) response shape the question/choice list sits, either a `questions`-style top-level list gets truncated from the tail (dropping later questions, possibly including `client_org`), or — if the bulk of the size lives inside a nested `definition` dict that isn't a top-level list — the function falls through to the "too large, not list-shaped" branch and the whole definition is silently discarded regardless of which question needed it.

## Product design

### Goals / Non-goals

**Goals**
- An agent can retrieve one named question's full definition — including every choice's custom properties (`tenantId`, `haloClientId`, `rewstOrgId`) — from a form of any size, without that data being silently dropped by response-size capping.
- The fix generalizes to any form/question, not just f7528a78/client_org specifically.
- Existing callers that don't ask for a single question see byte-for-byte unchanged behavior.

**Non-goals**
- Changing the backend "survey" API itself (we don't own it; `api_client.py:13-18` already documents the gap between the contract doc and the real gateway route).
- Changing the general `include=["questions"]` compact projection's documented shape (name/kind/title/required/showIf) for all callers — that is a separate, larger contract change that could affect other existing callers relying on it staying small.
- Raising the global 20,000-char cap for all tool calls — that trades away the budget guarantee `_json.py` exists to provide, for every tool, to fix a problem specific to reading one question's choices.
- Any UI change to the Forms app itself (out of scope; this bug is in the MCP layer agents call, not the web app wiki patrols).

### Approach (user-visible / tool-contract behavior)

#### Main flow
1. An agent (or any `mspbots_forms_form_get` caller) that needs full metadata for one specific question supplies a new optional parameter identifying that question (see AC1).
2. The tool fetches the form's full definition from the backend and returns just that one question's object — `name`, `title`, `type`, and its full `choices` array with every per-choice property intact — instead of the whole form.
3. Because the returned payload is scoped to a single question, it stays well under the 20,000-char budget for realistic question sizes, so nothing needs to be dropped.

#### Interface & interaction changes
This is a tool contract (MCP), not a UI — there is no screen. The observable surface is the JSON returned by `mspbots_forms_form_get`:
- New optional input: an identifier for a single question (AC1/AC3).
- New response shape when that identifier is given: the single matched question's fields at the top level of the result (not nested under a wrapper key — see Tech design §4 for why this matters), rather than the whole-form shape returned today.
- Existing call shapes (no new parameter) are unchanged (AC4).

#### Edge cases & exceptions
- Unknown/misspelled question identifier → a clear, structured error, not a silent empty or wrong result, and not a fallback to returning the whole form (AC3).
- A single question whose own choice list is unusually large (hypothetically large forms/questions beyond today's 41-question/client_org case) → the response must still truncate gracefully (keep as many whole choices as fit, flag that it did so) rather than reproduce today's bug of losing the data entirely (AC2).

#### Permissions & multi-tenancy
No new permission surface. This change only reshapes which part of an already tenant-scoped, already-authenticated response gets returned — tenant isolation is enforced upstream, unchanged, via the existing API key + `X_Tenant_ID` cookie (`api_client.py:73-111`). AC6 is a regression guard confirming the new code path doesn't introduce any new shared/cross-request state that could leak between tenants.

### Impact surface

- Affects only `mspbots_forms_form_get` callers in `mspbots-forms-mcp`. No other tool in this repo is touched.
- Backward compatible: the new parameter is optional and additive; every existing caller (any agent/skill currently calling this tool without the new parameter) is unaffected.
- No data migration, no change to stored forms/responses, no change to the backend survey API.
- Unblocks SOP 230 R-07 client-to-tenant mapping for the Ginko offboarding milestone once the matching config/skill change (out of scope here — PM/Micus's scope, not this ticket) consumes the new parameter.

### Acceptance criteria AC1..AC6

- **AC1**: Given the offboarding form f7528a78 has a `client_org` question whose choices carry `tenantId`, `haloClientId`, and `rewstOrgId`, When an agent calls `mspbots_forms_form_get` with that question identified by name, Then the response contains that question's full `choices` array and every choice retains all three properties.
- **AC2**: Given the identified question's own choice list is large enough that returning it in full would exceed the tool's existing response-size budget, When the same filtered call is made, Then the response is still well-formed JSON containing as many whole choices as fit (no choice is returned with any of its own properties missing), and the response is explicitly marked as truncated with the original count — it must never fall back to discarding the question entirely.
- **AC3**: Given a question identifier that does not match any question in the form, When the filtered call is made, Then the response is a clear, structured error indicating no such question was found — not a silent empty payload, not the whole form as a fallback, and not an unhandled exception.
- **AC4**: Given an existing caller that does not supply the new question identifier, When it calls `mspbots_forms_form_get` exactly as it does today, Then the response is unchanged from current behavior (same shape, same truncation rules as before this change).
- **AC5** *(manual — live verification, cannot be exercised from this sandbox; see Current state's wiki/sandbox note)*: Given the real offboarding form f7528a78 v4 in the MSPbots demo tenant, When an operator with PROD/INT access calls the fixed `mspbots_forms_form_get` for the `client_org` question, Then the live response contains every real `client_org` option with real `tenantId`, `haloClientId`, and `rewstOrgId` values intact — this is the literal acceptance criterion the reporter stated on the ticket.
- **AC6**: Given two different tenants each call the filtered `mspbots_forms_form_get` for their own forms, When both calls are made, Then neither response is affected by the other tenant's data or credentials — the new code path introduces no new shared or cross-request state beyond the existing per-request client/tenant plumbing in `api_client.py`.

### Scope split

- **This ticket (MVP)**: add the single-question filter to `mspbots_forms_form_get` (AC1-AC4, AC6, automatable now); AC5 is a manual, live-environment check to be run once the code ships to an environment with real tenant data.
- **Explicitly out of scope / later**: extending the compact `include=["questions"]` projection to carry choice-level properties for all callers; any change to the backend survey API's own size limits; the downstream skill-config consumer that will actually use the new parameter for SOP 230 R-07 (that's a separate piece of work, not this MCP tool).

### Open questions

- **[already assumed]** Whether the historical truncation the reporter observed was caused by the `include=["questions"]` compact mode (which never carries choice properties by design) or by `dump_json_capped`'s size-based truncation on `include=["definition"]` is not confirmed — no live reproduction was available from this sandbox. Assumption: it does not matter which one it was, because the fix in this design (a dedicated single-question filter, §Tech design) bypasses both paths for the targeted question regardless of which one caused the original symptom. Not blocking; if a live repro later shows a third, unrelated mechanism, only the Tech design's change list would need revisiting, not this product design.
- **[already assumed]** The parameter identifies a question by its SurveyJS `name` (e.g. `"client_org"`), matching how the reporter referred to it and how `mspbots_forms_form_update`'s existing docstring already uses `name` as the per-question identifier (`forms.py:159-163`). If product wants matching by question `title` text instead, that's a smaller follow-up to the same change.
- **[not blocking]** Whether other large forms beyond f7528a78 hit the same symptom is assumed yes in general (same code path serves every form), so the fix is written to be form-agnostic rather than special-cased to f7528a78.

## Tech design

### Conclusion

Add an optional `field_id` parameter to `mspbots_forms_form_get` (`forms.py:60-87`). When supplied, always fetch the backend's full `include=definition` response, locate the one question whose SurveyJS `name` matches `field_id` by walking the definition's page/element tree (including nested `panel` elements), and return that question's own fields spread at the top level of the result (not nested under a wrapper key) so `dump_json_capped`'s existing top-level-list truncation can still correctly cap an unusually large `choices` array if needed. No backend, database, or other-tool changes.

### Where the current implementation lives

- `src/mspbots_forms_mcp/tools/forms.py:60-87` — `mspbots_forms_form_get`, the tool being extended.
- `src/mspbots_forms_mcp/tools/forms.py:66-69` — existing `include` semantics (`definition`/`questions`/`versions`), unchanged by this design.
- `src/mspbots_forms_mcp/_json.py:18-61` — `dump_json_capped`, reused as-is; its top-level-list truncation behavior is the mechanism this design relies on to cap an oversized `choices` array (AC2).
- `src/mspbots_forms_mcp/api_client.py:118-119` — `FormsAPIClient.get`, used unchanged to fetch `include=definition`.
- `src/mspbots_forms_mcp/tools/forms.py:159-163` — the closest existing precedent for identifying a question by `name` (in `mspbots_forms_form_update`'s docstring), used here to justify the `field_id` = SurveyJS `name` choice in Open questions above.
- No DB layer exists in this repo (it is a thin MCP wrapper over an external REST API; `api_client.py` is the entire data-access surface) — there is no "where the current implementation lives" beyond these two files for this change.

### Change list

- `src/mspbots_forms_mcp/tools/forms.py` **[changed]** — `mspbots_forms_form_get`:
  - Add `field_id: Annotated[str | None, Field(description=...)] = None` parameter.
  - When `field_id` is given: force the backend call's `include` to contain `"definition"` (merged with any caller-supplied `include` values, de-duplicated) regardless of what else was asked for, since the question tree only exists under `definition`.
  - After the backend responds, call a new helper (see next bullet) to find the matching question; if found, build the response dict by spreading the question's own keys at the top level (plus `form_id` and `field_id` for context) and pass it through the existing `dump_json_capped`; if not found, return `error_envelope("not_found", f"No question named {field_id!r} in form {form_id}", False)` (same pattern already used by every other error path in this file).
  - Update the tool's docstring to document the new parameter and to make explicit that `include=["questions"]` (compact mode) never carries choice-level custom properties — callers needing those must use `field_id`.
- `src/mspbots_forms_mcp/tools/forms.py` or a new small module (e.g. `src/mspbots_forms_mcp/tools/_survey_walk.py`) **[new, implementer's choice of file]** — a helper, e.g. `find_question_by_name(definition: dict, name: str) -> dict | None`, that walks `definition["pages"][*]["elements"][*]` recursively (an element of SurveyJS type `"panel"` nests its own `"elements"` list — the walk must recurse into those too) and returns the first element whose `"name"` equals the given name, or `None`.
- `tests/test_tools.py` **[changed]** — new test cases per Test strategy below.
- No change to `src/mspbots_forms_mcp/api_client.py`, `server.py`, `config.py`, or any other tool file.

Not found in this repo and therefore not touched: any DB migration path, any backend route change, any UI code (none exists here).

### Data & API contract

**Tool parameter (MCP-level, not REST — this is an in-process Python function signature change)**

- New: `field_id: str | None = None` on `mspbots_forms_form_get`. Backward compatible — omitted means identical behavior to today.
- Semantics: matches a SurveyJS question element's `"name"` property inside the form's `definition` (see Open question on `name` vs `title`).

**Backend REST call (unchanged endpoint, same as today)**

- `GET {base}/surveys/{form_id}?include=definition` (and any other `include` values the caller also passed, de-duplicated) — same endpoint `api_client.py` already calls; only the `include` value passed is adjusted when `field_id` is present.

**Tool response shape**

- Without `field_id` (today, unchanged): whatever shape `include` produces today, passed through `dump_json_capped`.
- With `field_id`, question found:
  ```json
  {
    "form_id": "f7528a78",
    "field_id": "client_org",
    "name": "client_org",
    "title": "Client Organization",
    "type": "dropdown",
    "choices": [
      {"value": "...", "text": "...", "tenantId": "...", "haloClientId": "...", "rewstOrgId": "..."}
    ]
  }
  ```
  **Design requirement, not a suggestion**: the question's own fields (including `choices`) must be spread at the *top level* of this dict, not nested as `{"question": {...}}`. `dump_json_capped`'s truncation only scans top-level dict keys for a `list` value (`_json.py:31`) — if `choices` were nested one level deeper under a `"question"` key, an oversized `choices` array would not be found and capped; the whole response would instead fall into the "too large, not list-shaped" branch and be discarded entirely, silently reproducing the exact bug this ticket is about. The flattened shape above is what makes AC2 true.
- With `field_id`, question not found: `error_envelope("not_found", "No question named '<field_id>' in form <form_id>", False)` — same JSON shape every other error in this file already returns (`api_client.py` → `FormsAPIError.to_envelope()`, or `_json.error_envelope` directly, matching the existing pattern at `forms.py:266-269`).

**Backward compatibility**: fully additive. No existing caller's request or response shape changes.

### Key flow / sequence

```
agent -> mspbots_forms_form_get(form_id, field_id="client_org")
      -> client_factory() -> FormsAPIClient (unchanged)
      -> client.get(f"/surveys/{form_id}", params={"include": "definition"})   # forced when field_id given
      -> backend returns full SurveyJS definition (unchanged backend call)
      -> find_question_by_name(definition, "client_org")   # new helper, walks pages/elements (+ nested panels)
            -> found: question dict
            -> not found: None
      -> found: dump_json_capped({"form_id": ..., "field_id": ..., **question})
      -> not found: error_envelope("not_found", ...)
      <- single-question JSON (or error) returned to caller
```

### Non-functional

- **Idempotency & concurrency**: `mspbots_forms_form_get` is already read-only (`ToolAnnotations(readOnlyHint=True)`, `forms.py:59`); the new code path adds no writes and no new state, so it is trivially idempotent and safe under concurrent calls.
- **Performance**: one backend GET per call, same as today (no N+1 introduced) — the new behavior forces `include=definition` instead of a lighter `include` value when `field_id` is given, which is a slightly larger upstream payload than `include=questions` would be, but it is fetched once and filtered client-side; no additional round trips.
- **Security**: no new auth surface; reuses the existing `FormsAPIClient` (API key header + `X_Tenant_ID` cookie, `api_client.py:103-111`) unchanged. No new data is exposed beyond what `include=definition` already returns today to any caller who asks for it — this change only changes which *slice* of that same data a caller can ask for.
- **Multi-tenant isolation**: unaffected — see AC6. The new helper function (`find_question_by_name`) is a pure function operating only on the already-tenant-scoped `definition` dict passed into it; it holds no state across calls and reads no tenant/credential data itself.
- **Observability**: this repo has no logging framework in the files touched (confirmed by inspection — `forms.py`/`api_client.py` have no `logging` import); consistent with that, no logging is added by this change. If a future ticket adds structured logging to this repo, the new error path should emit at that time too — out of scope here.

### Rollout & rollback

- No feature flag — this is a pure additive parameter on a read-only tool in a standalone MCP server repo (not a UI, not a multi-service rollout).
- Rollout: ship directly to `main` (this repo's own line-to-ship branch per `references/clickup.md`'s branch table — github.com repos here use `main`, no `release` branch exists for this repo) once code review passes; no deployment ordering dependency on any other repo.
- Rollback: revert the commit. No data migration, no schema change, no external API change — a revert fully restores prior behavior with no cleanup needed.

### Test strategy

- Unit tests (new, in `tests/test_tools.py`) for the new helper and the new `field_id` branch, using a mocked `FormsAPIClient.get` returning a synthetic SurveyJS `definition` fixture containing a `client_org` dropdown question with `choices` carrying `tenantId`/`haloClientId`/`rewstOrgId` — see Test cases below for the exact AC-to-test mapping.
- Regression coverage: a test asserting that calling `mspbots_forms_form_get` **without** `field_id` returns byte-identical output to before this change, for the same mocked backend response (AC4).
- No automated end-to-end test against the live backend is possible — this repo's own README (`README.md:231`) already notes write tools are deliberately never exercised against real PROD data, and this sandbox has no path to a live tenant (consistent with this pipeline's own experience that development sandboxes typically cannot reach live backend services). AC5 is therefore a manual, live-environment test case, to be run by whoever has PROD/INT access once this ships.
- Regression面: only `mspbots_forms_form_get` is touched; no other tool in this repo calls the new helper or the changed branch, so the regression surface is limited to that one tool's existing callers (AC4 covers them).

### Effort & breakdown

- Estimated 0.5–1 day for a single engineer: the helper function (~20-30 lines), the parameter wiring in `forms.py`, docstring update, and the unit tests in Test strategy above. The main source of uncertainty is confirming the SurveyJS `pages[].elements[]` (+ nested `panel`) shape against a real backend response if one becomes available during implementation — the file's own disclaimer (`forms.py:1-12`) means this shape has not been independently verified beyond one smoke test.
- Suggested as a single sub-task — the change is small enough that splitting it further would add coordination overhead without a clear independent-verification benefit.

### Risks & dependencies

- **Risk**: the SurveyJS `pages → elements (+ nested panel elements)` tree shape assumed by the new helper is the standard public SurveyJS JSON schema, but this repo's own header (`forms.py:1-12`) states even the base `definition` shape has not been independently verified beyond a single 2026-08-07 PROD smoke test for a different (unspecified) form. If the real backend's `definition` shape differs (e.g. a flat `elements` list with no `pages` wrapper, which some SurveyJS configurations use), the helper's page/element walk needs adjusting. Mitigation: AC5's manual live check against the real f7528a78 form will surface this quickly; the helper should be written as a small, isolated function specifically so it's a one-function fix if the real shape differs.
- **Risk**: the root cause of the originally reported truncation is not confirmed (Open question above) — this design's fix resolves the user's stated need regardless of which mechanism caused it, but if a live repro later shows a third, unrelated mechanism, this ticket's fix may need a follow-up (not expected to block this ticket's own ACs, which are testable independent of the historical root cause).
- **Dependency**: none on other open tickets. The downstream consumer (whatever skill/config actually calls `mspbots_forms_form_get(field_id="client_org")` for SOP 230 R-07) is explicitly out of scope for this ticket (see Scope split) and is a separate piece of work the reporter's team owns.
