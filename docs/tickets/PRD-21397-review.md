### Findings

1. [must-fix] `src/mspbots_forms_mcp/tools/transfer.py:113-130` — `mspbots_forms_form_import` drops form-level settings on import, so AC2 (settings fidelity) is not actually implemented. The import tool extracts only `form.get("title")` and `form.get("definition")` from the exported record and PATCHes the new form with just `{"definition": ..., "title": ...}`. But `showProgressBar` is a sibling field on the form record, not nested inside `definition` — proven by the existing `mspbots_forms_form_create`/`mspbots_forms_form_update`/`mspbots_forms_form_quick_publish` tools in `forms.py:135-136,210-211,319-320`, which all accept `show_progress_bar` as a parameter separate from `definition` and write it to `body["showProgressBar"]` as a top-level key. Since the export payload's `form` object is the raw base record (same shape `form_get` returns), it will contain `showProgressBar` (and almost certainly whatever field holds "requires Microsoft 365 sign-in" and the thank-you message, per AC2's own wording) at the top level too — and the import code silently discards everything except `title`/`definition`. AC2 explicitly requires progress bar, M365 sign-in, and thank-you message to be identical after import; as written, none of those settings survive the round trip, only the question/page structure does. Note the tech design's own "Change list" (`docs/tickets/PRD-21397.md:94`) already says the PATCH body should include `"showProgressBar": ...` — the shipped code doesn't do it, so this is also a design/implementation mismatch, not just an untested edge.
   Fix: carry over the form-level settings fields (at minimum `showProgressBar`; ideally construct the PATCH body from the full base record minus `id`/response-bearing fields, the same way `form.get("definition")` is extracted) in the `client.patch(...)` call at `transfer.py:128-131`.
   This is why TC2 (AC2) matters as more than "needs a real account" — it isn't just unexercised, the code path it would exercise doesn't do the thing AC2 asks for.

### Findings

1. [must-fix] `src/mspbots_forms_mcp/tools/_transfer_sanitize.py:82-99` (`_walk`) — the tenant-scoped static-choice stripper only looks at a top-level `choices` list (`node.get("choices")`), but the *real* backend shape for a static-choice question is `choicesSource: {"items": [...], "passAttributes": [...]}`, not a top-level `choices` list — this is not speculation, it was live-tested and fixed on the sibling ticket PRD-21379 in this same repo, merged into `main` as `7f2f83e`/`0aa749b` ("`fix(forms): normalize choicesSource into a top-level choices list (PRD-21379 r2 / AC7)`", `src/mspbots_forms_mcp/tools/_survey_walk.py`'s `normalize_choice_source` docstring: *"the real client_org question on form f7528a78 actually uses [choicesSource]"*). That is the exact same question this ticket's own design cites as the target case: `docs/tickets/PRD-21397.md:56` (AC5) — *"the `client_org` options on Ginko's form"*, keys `tenantId`/`haloClientId`/`rewstOrgId` — and `TENANT_SCOPED_CHOICE_KEYS = {"tenantId", "haloClientId", "rewstOrgId"}` in `_transfer_sanitize.py:21` names the identical keys. Since `_walk` never inspects `choicesSource.items`, a question shaped like the real Ginko/client_org one will not be detected at all — `node.get("choices")` is `None`, the tenant-scoped-keys branch never runs, `choices`/`choicesSource` pass through untouched — so the import carries `tenantId`/`haloClientId`/`rewstOrgId` values straight into the destination tenant. This is a cross-tenant data-isolation failure (`legs/review.md` R3 "安全" row: "多租户数据没按租户隔离"), not a cosmetic gap, and it defeats AC5 for the one real-world shape the ticket was written to cover — `tests/test_transfer.py`'s TC5/TC6 fixtures only exercise the assumed top-level-`choices` shape (round-1's guess, written before PRD-21379's live test disproved it for this field type), so they pass without exercising the real shape at all.
   Fix: `_walk` needs to normalize/recognize `choicesSource.items` the same way `normalize_choice_source` (`_survey_walk.py`, already in `main`) does for `forms_get`, before running the `TENANT_SCOPED_CHOICE_KEYS` check — and `choicesByUrl` under a `choicesSource` shape (if that combination is possible) needs the same check. Add a fixture shaped like the real `choicesSource: {"items": [{"value": ..., "tenantId": ...}, ...]}` to `tests/test_transfer.py` (mirroring PRD-21379's TC7 fixture) to lock this in — the existing TC5/TC6 fixtures are not sufficient evidence this works. This repo's `main` has moved past this ticket's declared base (`main@35c6ccf`) specifically because of this fix (PRD-21379, merged `main@0aa749b`, 2026-10-29); whichever round re-syncs with the current default branch should pull `_survey_walk.py` in and reuse `normalize_choice_source` rather than re-deriving the same logic.

2. [must-fix] `src/mspbots_forms_mcp/tools/transfer.py:133-136` — the round-1 fix builds the PATCH body from `{k: v for k, v in form.items() if k not in {"id", "definition", "questions", "versions"}}`, i.e. every other top-level key on the raw form record is carried over unexamined. The ticket's own non-goals are narrower than that: `docs/tickets/PRD-21397.md:45` — *"Copying submitted responses, the original form ID, owners/sharing, or trigger links"* — is explicitly out of scope, and the Scope section (`:39`) requires the imported form to be "**unpublished**". Nothing in the excluded-keys set accounts for an owner/sharing field or a publish/status field, and this repo's own code makes it likely the base record has one: `forms.py:33-34,52` filters `mspbots_forms_form_list` by `status` ("draft"/"published"/"archived"), and `shares.py` has a parallel, separate `status`-driven state machine for share links — strong evidence the base `/surveys/{id}` record carries at least a `status` field alongside `definition`. If the source form is published, blindly copying `status` (or whatever key holds sharing/ownership) into the PATCH body of the freshly created (currently-draft) form risks publishing it on creation, and/or carrying over the source's sharing/ownership metadata — both directly contradicted by the ticket text above. `forms.py:1-12`'s own disclaimer ("built entirely from the API contract pasted into ClickUp... none have been called against a real deployment") means this can't be ruled out by reading the code alone, and the original tech design (`docs/tickets/PRD-21397.md:132`, Data & API contract step 5, still reads `{"definition": stripped_definition, "title": ...}` — never updated to match either round's shipped PATCH body) deliberately scoped the PATCH body narrowly, which this blanket-copy approach abandons without addressing the fields it was presumably narrow to protect.
   Fix: either enumerate the settings keys actually needed for AC2 (progress bar / M365-sign-in / thank-you-message, once TC2 on a real form identifies their real names) instead of a blanket copy, or keep the blanket-copy approach but extend the exclusion set to also drop anything status/owner/sharing-shaped (and confirm against a real form via TC2 which keys those are, same as AC2's own open-question dependency). Either way, `tests/test_transfer.py::test_import_carries_over_sibling_form_settings` should also assert that a `status`/owner-shaped key on the source form is *not* in the PATCH body, the same way it already asserts `id`/`questions`/`versions` are excluded.
