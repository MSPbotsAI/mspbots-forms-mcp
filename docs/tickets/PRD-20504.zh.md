## 需求理解

一句话：为 MSPbots Forms MCP 增加对指定表单内记录的生产级增删改查（带过滤与分页的列表/查询、按 ID 获取、创建、更新、删除），并保留租户级授权与表单自身的校验规则，用于 Ginko 组织映射迁移场景。

MSPbots Forms MCP 目前只支持搭建/发布表单，以及读回已提交的答卷（一个列表视图、一个聚合统计视图）——agent 没有办法创建、更新或删除单条记录。提单人希望 agent/工作流能以编程方式维护某个表单内的结构化"记录"，首个具体用例是 Ginko 工作流迁移所需的跨系统组织 ID 映射表（NinjaOne 组织 ID、Huntress 组织 ID、IT Glue 组织 ID、HaloPSA 客户 ID、ConnectWise 公司名等）。成功的标准是：agent 能安全地列表/过滤/翻页、按 ID 获取、创建、更新、删除某个表单内的记录——同时保留该表单自身的校验规则与租户级授权——不需要回退到手工 UI 维护。

## 现状

- `mspbots-forms-mcp` 暴露 14 个工具，分三组：Form（list/get/create/update/publish/delete/quick_publish）、Share（list/get/create/update/delete）、Response（summary、list）——`src/mspbots_forms_mcp/tools/forms.py:32-341`、`src/mspbots_forms_mcp/server.py:104-126`。
- Response 组是只读的。`mspbots_forms_response_list`（`src/mspbots_forms_mcp/tools/responses.py:46-84`）以紧凑的列式格式列出已提交答卷，支持 `status`/`share_id`/`cursor`/`limit` 过滤；`mspbots_forms_response_summary`（`src/mspbots_forms_mcp/tools/responses.py:26-44`）返回按问题聚合的统计数据。仓库里没有任何工具支持单条 response/record 的按 ID 获取、创建、更新或删除。
- 目前唯一能写到单条记录的路径是**公开的、无需认证的答题人提交流程**（`/api/public/*` —— unlock/save-draft/submit）。本 MCP 刻意**不**把它暴露成工具："an agent shouldn't be able to submit a form on an anonymous respondent's behalf"（`README.md` Overview 小节，约第 63-68 行）。
- 这整套后端 API（`/apps/app-forms/api/...`）是照着粘贴进 PRD-15818 的 API 契约文档实现的，没有读过真实后端源码——"the actual backend repository was not read"（`README.md` 第 9 行）。那个后端仓库**不在**本流水线当前可用的 `Code Project` 选项里（2026-10-14 用 `mbp.py project list` 核实），所以除了本 MCP 代码里已经调用的那部分，其真实端点面无法靠读代码验证。
- wiki：实际产品里 Forms app 的 Responses 页面是一张只读表格（`Status` / `Submitted` / 每个表单字段各一列），页脚 `"Showing N of N"`；巡检时"单条记录详情视图（如果有的话）没有被打开过"——`ProductDocs/Apps/forms/12-Responses.md`（_verified_ 2026-08-13, v0.0.9）。wiki 里没有任何一页把"表单当结构化数据表"记录为一个与问卷答卷不同的用法——这是一个未核实的缺口，不是一个已确认的"没有这功能"。
- 两次历史记录提醒这份契约本身不可全信：2026-08-07 发现真实 host 路径（`/apps/app-forms/api/...`）与契约文档不符，2026-08-26 发现"仅 PROD 部署"的假设已经过期（`README.md` Known Gaps 小节）。任何新契约在联调前都应假设可能有类似出入。

## 产品设计

### 目标 / 非目标

目标：
- Agent/工作流能对一个指定表单：带过滤与分页地列表/查询记录、按 ID 获取单条、创建、更新、删除。
- 返回结构化 JSON，清楚暴露 `form_id` 与 `record_id`。
- 写操作强制执行表单自身的字段校验（类型、必填、choices），租户级授权与本 MCP 其它工具一致。
- 这个最小可用版本要能完整覆盖 Ginko 组织映射这一首发用例。

非目标：
- 不触碰、不替换、不重新暴露公开的匿名答题人提交流程。
- 不做记录级的版本历史/审计 UI（除非产品另行提出，后端自身的日志不在此列）。
- 不做批量导入/导出工具（Forms UI 已有的 Export CSV 不在本次范围）。
- 不改动 Forms 前端应用。

### 验收标准 AC1..AC5

- **AC1**：Given 一个已存在的表单 ID, When agent 调用记录列表/查询工具并带过滤条件（如 status）与分页上限, Then 只返回归属该表单的匹配记录，并带 `nextCursor` 支持继续翻页——绝不出现其它表单或其它租户的记录。
- **AC2**：Given 一个已知的 `record_id`, When agent 调用按 ID 获取工具, Then 返回该条记录完整的结构化字段数据；若 id 不存在或属于另一个表单则返回 `not_found`；Given 一个表单及合法的字段值, When agent 调用创建/更新/删除, Then 对应记录被创建/更新/删除，后续 get/list 能反映这个变化——删除需要显式 `confirm=true`，与现有 `form_delete`/`share_delete` 的模式一致。
- **AC3**：Given 一次创建或获取记录的返回结果, When 解析它, Then 其中明确包含 `form_id` 与 `record_id`（不是仅嵌套在某个值里）——结果是结构化 JSON，不是临时拼接的字符串。
- **AC4**：Given 一次创建/更新请求携带违反表单自身字段定义的值（必填项缺失、值不在 `choices` 之内、类型不对）, When 提交, Then 请求被拒绝（映射到现有的 `invalid_argument` 错误包），且不会产生半写入的记录；Given 一次跨租户调用（`record_id` 属于租户 B，但调用方凭据是租户 A）, When 对它调用任意记录工具, Then 返回 `not_found` 或 `unauthorized`，且不泄露该记录的存在或内容。
- **AC5**：Given Ginko 组织映射场景的字段集（NinjaOne/Huntress/IT Glue/HaloPSA/ConnectWise 等标识符）, When agent 只用这组新工具跑完整个生命周期（创建→更新一个字段→列表确认→删除）, Then 全部步骤都能成功完成，不需要回退到手工 UI 维护。

### Open Questions

- **[已假设]** 真实后端（`app-forms`）的代码不在本流水线可读范围内，而其已知契约里**完全没有任何认证态的单记录读写端点**——只有只读的 list+summary，以及匿名的公开提交流程。本设计**假设**后端团队会新增一组认证态的单记录 CRUD 端点（形状见技术设计 §5）。如果后端团队决定扩展现有的 `/responses` 资源而不是新建独立的 `/records` 资源，技术设计第 4/5 节需要重写。这是一个后端归属方需要确认的决定，本流程无法替它做。
- **[已假设]** 本设计假设在产品语义上"记录"应该与答题人提交的"response"区分开——即 agent 创建的记录**不应该**计入面向答题人的分析指标（`totalStarted`/`totalCompleted`/`completionRate`）。原因见技术设计 §3。如果产品认为两者就是同一份数据、agent 的写入应该和正常提交一样计入统计，第 3/5 节需要重做。
- **[不阻塞]** "Ginko" 在产品事实库（wiki）里完全没有命中——无法确认是否已有现成的组织映射表单模板或命名约定。按工单字面意思继续推进，不影响工具层本身的设计。
- **[不阻塞]** `app-forms` 后端仓库不在当前 79 个有效的 `Code Project` 选项里（2026-10-14 核实）——这个依赖项无法仅凭本工单推进，很可能需要针对持有该后端的仓库另开一张工单，或在 groom 时明确说明范围。

## 技术设计

### 结论

在 `mspbots-forms-mcp` 新增一组工具——`mspbots_forms_record_list/get/create/update/delete`——背后是一个**全新的、独立的资源**（`/surveys/{form_id}/records`），原样复用本仓库已有的 client/错误/分页/删除确认等基础设施。MCP 层只负责参数整形与转发；字段校验与租户隔离仍留在它们本来就在的地方——后端 API，和其它所有写工具一致。这是最省的方案，因为它原样复用 `FormsAPIClient`、`error_envelope`、`dump_json_capped` 与 `confirm=true` 安全模式，而不是重新发明一套管线。**最关键的前提是：`app-forms` 后端需要新增这些端点——这部分工作在本仓库之外，无法在这里验证或实现。**

### 现有实现定位

- `src/mspbots_forms_mcp/tools/forms.py:32-145` —— list/get/create 的分页（`cursor`/`limit` 钳制到 100）与 DSL 校验模式；新 record 工具应照此形状写。
- `src/mspbots_forms_mcp/tools/forms.py:242-277` —— `form_delete` 的 `confirm=true` 安全阀；`record_delete` 应复用同一约定。
- `src/mspbots_forms_mcp/tools/responses.py:46-84` —— `response_list` 现有的 `status`/`share_id`/`cursor`/`limit` 过滤与分页形状；`record_list` 应匹配它以保持一致（同样钳制到 100，同样的 cursor 语义）。
- `src/mspbots_forms_mcp/api_client.py:98-192` —— `FormsAPIClient` 已经封装了 GET/POST/PATCH/DELETE、重试与租户 cookie；record 工具直接调用它，不需要新的 client 代码。
- `src/mspbots_forms_mcp/_json.py:76-77` 与 `src/mspbots_forms_mcp/tools/_common.py:1-7` —— `error_envelope`、`NO_TOKEN` 原样复用。
- `src/mspbots_forms_mcp/server.py:99-140` —— 需要新建 `tools/records.py` 模块并在此处 `register()`，同时 `mcp.instructions` 的工具分组说明需要补一句（注意 ≤1500 字符的断言，见非功能/测试策略）。
- `tests/test_tools.py:14-56` —— 工具清单快照测试：`EXPECTED_TOOLS` 与 `len(tools) == 14` 这条断言都要跟着新工具同步改（改成 19）。

### 方案选型

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A. 扩展现有 `/responses` 资源，加 POST/PATCH/DELETE | 复用 `response_id`，在同一资源上加写方法 | 改动面最小，路径复用 | 把"面向答题人的分析统计"和"agent 维护的结构化数据"混为一谈——agent 的写入会污染本该反映真实答题人行为的 `totalStarted`/`completionRate`，而且直接违背 README 明确写下的安全原则（agent 不应代表答题人行事） | 不选 |
| B. 新增独立的 `/records` 资源，与 `/responses` 并存 | 新路径 `/surveys/{id}/records`；存储方式由后端决定（新建一张表，或复用同一张表但打 `source=agent` 标记） | 语义清晰；不污染答题人分析统计；未来可以区分 agent 写入与答题人提交做审计 | 需要后端新建一整套端点——一个本仓库自身改动无法独立满足的跨仓库依赖 | **选此项** |

没有其它自然可选方案——这个能力缺口无法只靠前端或 MCP 层的技巧绕过去，不管选哪个方案都需要后端新增能力。

### 数据与接口契约

（以下为假设，待后端确认——见 Open Questions / 风险与依赖）

- `GET /apps/app-forms/api/surveys/{form_id}/records?status=&cursor=&limit=` → `{"items": [{"id": str, "formId": str, "status": str, "createdAt": str, "updatedAt": str, "fields": {<question name>: <value>}}], "nextCursor": str|null}`。与 `response_list` 的列式格式不同，记录用一个按问题名为 key 的 `fields` 对象——记录是给程序消费的，不是给人看的，所以不需要 response_list 那种省 token 的列式优化。
- `GET /apps/app-forms/api/surveys/{form_id}/records/{record_id}` → 同样的单对象结构；404 → `{"error": {"code": "not_found", ...}}`。
- `POST /apps/app-forms/api/surveys/{form_id}/records` body `{"fields": {...}}` → 201 + 新记录；字段校验失败 → 422（映射到现有的 `invalid_argument` 错误包）。
- `PATCH /apps/app-forms/api/surveys/{form_id}/records/{record_id}` body `{"fields": {...}}` —— 这是部分合并还是全量替换，是一个需要后端团队确认的契约细节；本设计建议部分合并（照 `form_update` 对 `definition` 字段"浅合并"的先例），但这一点尚未落定。
- `DELETE /apps/app-forms/api/surveys/{form_id}/records/{record_id}` → 204；MCP 工具只在 `confirm=true` 时才转发这个请求。
- 向后兼容：这是一个全新的资源——不触碰任何现有端点或工具，不需要迁移。

### 关键流程时序

Agent → `mspbots_forms_record_create(form_id, fields)` → `FormsAPIClient.post("/surveys/{id}/records", {fields})` → 后端按表单的问题定义校验 `fields` → `201 {record}` → MCP 返回 `dump_json_capped(record)`。
失败路径：字段值不合法 → `422` → `FormsAPIError` → `error_envelope("invalid_argument", ...)` → agent 看到的是结构化错误，而不是裸异常。

### 非功能

- **幂等与并发**：`create` 本质上非幂等（每次都新建一条）；`update`/`delete` 相对于目标记录的最终状态是幂等的，与 `form_update` 的 `idempotentHint` 一致。是否需要为并发更新同一条记录做冲突检测（`If-Match`/版本号）留给后端契约决定——标记为未落定的契约细节，本设计不下结论。
- **性能**：复用 `response_list` 现有的 `limit` 钳制（100）与 cursor 分页，避免一次性返回无界数据。Ginko 场景下记录数量级大约是"组织数量"（通常远低于 10^4），本次范围不需要额外的索引设计。
- **安全**：鉴权点与现有所有工具一致（`X-API-Key` + `X-MSP-Tenant-Id` → `X_Tenant_ID` cookie，由 app-routing 网关与后端业务层共同保证）。字段值可能包含客户的 PSA/工单系统标识符——属于租户数据而非凭据，但日志不应打印完整的 `fields` 内容，照抄现有 response 工具"从不记录单元格值"的做法。
- **多租户隔离**：这是 AC4 跨租户用例的核心。记录归属校验必须在后端完成；MCP 层既不做也结构性地做不到二次校验（它根本拿不到其它租户的凭据）。
- **可观测性**：原样复用 `FormsAPIError.to_envelope()`，让每个错误都带 `retryable` 标志供 agent 判断是否重试；不需要新增日志基础设施。

### 上线与回滚

本仓库没有 feature flag 机制（它是无状态 MCP——工具在服务用新代码重启后立刻生效）。按仓库既有的纪律，写路径应先在一次性测试表单上验证（INT 环境，绝不是 PROD），再合并。回滚就是简单地 revert 这个 commit，或者把这 5 个工具从 `server.py` 的注册列表里移除；现有 14 个工具不受影响。**但真正的上线顺序是：后端先上线新端点，本仓库再上线这组工具**——反过来做的话，这些工具调用全部会是 404 或 `upstream_error`。

### 测试策略

单测（本仓库，mock `httpx`，不碰真实网络）：工具清单快照更新、record CRUD 的参数整形、404/422/确认拒绝路径、cursor 透传。
集成/手工：后端端点就绪后，在一次性测试表单上跑一遍 create→get→update→list→delete 全链路（绝不对带真实数据的 PROD 表单做写操作，照抄 README 既有的写工具测试纪律）。
回归面：不影响现有 14 个工具；唯一共享状态的改动点是 `server.py` 的注册列表与 `mcp.instructions` 的字符长度——补一句说明之后仍需确认 ≤1500 字符这条断言（`test_service_instructions_present_and_bounded`）依然成立。

### 风险与依赖

- **硬依赖**：`app-forms` 后端必须新增记录级 CRUD 端点——这是本单能否交付的决定性因素，而它的仓库不在本流水线当前可触达的 `Code Project` 选项里。需要针对后端持有方另开工单，或在 groom 时明确在本单下确认范围。
- **风险**：契约细节（patch 还是全量替换的语义、并发冲突处理、"记录"和"response"分析统计是否区分）目前都是本设计的假设。一旦后端团队给出不同的形状，第 4/5 节需要重写。
