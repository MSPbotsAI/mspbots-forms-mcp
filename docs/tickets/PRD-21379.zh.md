# PRD-21379 · [Bug] Forms MCP truncates option properties

工单: https://app.clickup.com/t/86e3v7wzd
仓库: https://github.com/MSPbotsAI/mspbots-forms-mcp@main (4066e70)
工作分支: dev01.mbagent/PRD-21379
状态: 进行中

## 需求理解

一句话：提单人希望 `mspbots_forms_form_get` 对 offboarding 表单 f7528a78（41 题）能返回完整或过滤后的 client_org 题目，且每个选项的 tenantId、haloClientId、rewstOrgId 属性都保留，而不是像现在这样返回被截断、丢了这些属性的结果。

目前调用 `mspbots_forms_form_get` 读这个 41 题的表单时，返回结果缺了 `client_org` 题目做客户-租户映射所需的逐选项属性。没有这些属性，SOP 230 的 R-07 流程（从客户邮件预填 offboarding 表单）就没法解析出离职人对应的租户和转发对象，agent 只能把这些字段留空。目前用 skill 配置里的一份手工映射做临时绕过。Micus Zheng 于 2026-10-23 把单交给 dev01，优先级定为 `high`（不是 `urgent`，因为有绕过方案），并标注它会阻塞 Ginko SOP 230 offboarding 里程碑（Tier 1，11 月 7 日到期）。

## 现状（每条断言都带 path:line）

读取仓库：`https://github.com/MSPbotsAI/mspbots-forms-mcp@main (4066e70)`。

- `src/mspbots_forms_mcp/tools/forms.py:60-87` 是 `mspbots_forms_form_get` 的唯一实现。它接受 `form_id` 和可选的 `include` 列表（`"definition"`、`"questions"`、`"versions"`），用这个 `include` 参数调用后端 `GET /surveys/{form_id}`，再把结果原样经 `dump_json_capped`（第 85 行）返回。目前没有任何办法只要一个题目——这个工具只能在三种粒度之一返回整张表单。
- `src/mspbots_forms_mcp/tools/forms.py:66-69` —— `include="questions"` 的精简模式**本来就是按设计**只返回每题的 `name/kind/title/required/showIf`。它从未承诺会带上题目的 `choices` 数组，更不用说选项级别的自定义属性（`tenantId`/`haloClientId`/`rewstOrgId`）。如果调用方当初是用这个模式读 `client_org`，那些属性本来就不会出现——这不是这个模式下的截断缺陷，这就是精简视图写明的契约。
- `src/mspbots_forms_mcp/_json.py:11,18-61` —— `dump_json_capped` 对每个工具的 JSON 输出强制执行 `MAX_CHARS = 20_000`（第 11 行）的硬上限（模块文档第 1-6 行解释了这么做是为了让单次工具调用"永远不会超过一个 agent 上下文能合理消化的约 20,000 字符预算"）。当序列化后的载荷超过这个预算时，这个函数：
  - 只看**顶层** `dict` 的键里值为 `list` 类型的那些（`list_keys = [...]`，第 31 行）——嵌套在某个 dict 值里好几层深的列表（例如 `pages[].elements[].choices`）它根本看不到；
  - 如果存在这样一个顶层列表，就对这个列表二分查找能塞进预算的最大前缀，剩下的从尾部丢弃（第 35-52 行）——丢的是整条记录，不是记录里的某个字段；
  - 如果不存在顶层列表、而载荷仍然过大，就整个丢弃载荷，返回一条通用的"结果过大"提示（第 54-61 行）。
  对于一个用 `include=["definition"]` 请求、有 41 题的表单，完整的 SurveyJS 定义现实中很可能超过 20,000 字符；具体是哪种后果取决于（尚未独立验证，见下文）响应结构里题目/选项列表到底在哪一层——要么某个类似 `questions` 的顶层列表被从尾部截断（可能恰好丢掉包括 `client_org` 在内的后面几题），要么——如果体积主要在一个嵌套的 `definition` dict 里、它本身不是顶层列表——函数会落入"太大、又不是列表形状"的分支，不管哪个题目需要它，整个 definition 都会被静默丢弃。
- `src/mspbots_forms_mcp/tools/forms.py:1-12`（模块文档）：这整个工具文件除了 `README.md:230` 另外确认的部分，都标注着 `⚠️ UNVERIFIED —— 完全是照着贴进 ClickUp PRD-15818 的 API 契约写的……没有一个调用真实部署测试过`。`README.md:230` 说 `mspbots_forms_form_get`（包括 `include=questions`）在 2026-08-07 对一个真实 PROD 表单做过一次冒烟测试，"返回了形状正确的真实数据"——但该冒烟测试没有记录是否用的是 41 题的表单，也没有记录是否带选项级自定义属性，所以它既不能证实、也不能排除上面两种机制对这张具体表单的影响。
- `tests/test_tools.py` 里没有任何测试覆盖 `dump_json_capped` 的截断路径，也没有任何测试断言选项级自定义属性能在 `form_get` 调用中存活（已用 grep 核实——`choices`、`tenantId`、`truncat` 零命中）。就这个仓库自己的测试套件而言，用户反馈的这个行为在两个方向上都确实没人验证过。
- `tests/test_middleware.py`、`src/mspbots_forms_mcp/api_client.py` —— 客户端/租户隔离层（API key header + `X_Tenant_ID` cookie，`api_client.py:73-111`）与这个 bug 无关，下面考虑的任何方案都不会碰它。

## 产品设计

### 目标 / 非目标

**目标**
- agent 能从任意大小的表单中取出某一个指定题目的完整定义——包括每个选项的自定义属性（`tenantId`、`haloClientId`、`rewstOrgId`）——且这些数据不会被响应体积上限静默丢弃。
- 修复要通用于任意表单/题目，不是只给 f7528a78/client_org 打补丁。
- 不传这个新参数的现有调用方行为逐字节不变。

**非目标**
- 不改后端"survey" API 本身（我们不拥有它；`api_client.py:13-18` 已经记录过契约文档和真实网关路由之间的一处出入）。
- 不改 `include=["questions"]` 精简投影对所有调用方的既定形状（name/kind/title/required/showIf）——那是另一项更大的契约变更，可能影响其它依赖它保持精简的现有调用方。
- 不给所有工具调用统一抬高 20,000 字符上限——那会牺牲 `_json.py` 本来要为每个工具提供的预算保证，为的只是修一个"读单个题目选项"的特定问题。
- 不改 Forms app 本身的 UI（超出范围；这个 bug 在 agent 调用的 MCP 层，不在 wiki 巡检的网页应用里）。

### 方案（用户可见 / 工具契约行为）

#### 主流程
1. 需要某一个具体题目完整元数据的 agent（或任何 `mspbots_forms_form_get` 调用方）传入一个新的可选参数来指定这个题目（见 AC1）。
2. 工具向后端取整张表单的完整定义，只返回那一个题目的对象——`name`、`title`、`type`，以及它完整的 `choices` 数组、每个选项的属性都完整——而不是整张表单。
3. 因为返回的载荷只限于一个题目，对现实中的题目大小来说会远低于 20,000 字符的预算，所以不需要丢任何东西。

#### 界面与交互变化
这是一个工具契约（MCP），不是 UI——没有屏幕。可观察的表面是 `mspbots_forms_form_get` 返回的 JSON：
- 新的可选输入：单个题目的标识符（AC1/AC3）。
- 给出该标识符时的新响应形状：匹配到的那个题目的字段平铺在结果顶层（不是嵌套在一个包装键下面——原因见技术设计 §4），而不是今天的整表单形状。
- 不传新参数的现有调用形状不变（AC4）。

#### 边界与异常
- 未知/拼错的题目标识符 → 清晰的结构化错误，不是静默返回空结果或错误结果，也不会退回去返回整张表单（AC3）。
- 某个题目自己的选项列表异常大（假设性地，超出今天 41 题/client_org 这个案例的规模）→ 响应仍必须优雅截断（保留尽量多的、属性完整的整条选项，并标注已截断），而不是重现今天这种数据整体丢失的 bug（AC2）。

#### 权限与多租户
没有新增权限面。这次改动只是重新划分一个已经过租户限定、已经鉴权的响应里要返回哪一部分——租户隔离仍由上游既有的 API key + `X_Tenant_ID` cookie 机制负责，不变（`api_client.py:73-111`）。AC6 是一条回归保护，确认新代码路径不会引入任何可能在租户间泄漏的新共享/跨请求状态。

### 影响面

- 只影响 `mspbots-forms-mcp` 里 `mspbots_forms_form_get` 的调用方。本仓库其它工具都不受影响。
- 向后兼容：新参数是可选且纯增量的；任何现有调用方（当前不传这个新参数的 agent/skill）都不受影响。
- 没有数据迁移，不改已存储的表单/回答，不改后端 survey API。
- 一旦下游的配置/skill 改动（不在本单范围内，是 PM/Micus 那边的事）用上这个新参数，就能解除 SOP 230 R-07 客户-租户映射的阻塞，服务于 Ginko offboarding 里程碑。

### 验收标准 AC1..AC6

- **AC1**：Given offboarding 表单 f7528a78 有一个 `client_org` 题目，其选项都带 `tenantId`、`haloClientId`、`rewstOrgId`，When agent 用题目名调用 `mspbots_forms_form_get` 指定这个题目，Then 返回结果包含该题目完整的 `choices` 数组，且每个选项都保留全部三个属性。
- **AC2**：Given 被指定题目自身的选项列表大到完整返回会超出工具既有的响应体积预算，When 做同样的过滤调用，Then 响应仍是格式良好的 JSON，包含尽量多的、属性完整的整条选项（没有任何一条选项被部分裁剪掉属性），并且响应明确标注已截断及原始数量——绝不能退化成整个题目被丢弃。
- **AC3**：Given 一个在表单里找不到匹配题目的标识符，When 发起过滤调用，Then 响应是一条清晰的结构化错误，说明没找到这个题目——不是静默空载荷，不是退回整张表单，也不是未处理异常。
- **AC4**：Given 一个不传新题目标识符的现有调用方，When 它照今天的方式调用 `mspbots_forms_form_get`，Then 响应与这次改动之前完全一致（形状相同、截断规则相同）。
- **AC5**（*手工 —— 需要真实环境验证，本沙箱无法执行，见"现状"小节的 wiki/沙箱说明*）：Given MSPbots demo 租户里真实的 offboarding 表单 f7528a78 v4，When 有 PROD/INT 访问权限的人用修复后的 `mspbots_forms_form_get` 调用 `client_org` 题目，Then 真实响应里每个真实的 `client_org` 选项都保留真实的 `tenantId`、`haloClientId`、`rewstOrgId` 值——这就是提单人在工单上写下的验收标准原文。
- **AC6**：Given 两个不同租户各自调用过滤版的 `mspbots_forms_form_get` 读自己的表单，When 两次调用都发生，Then 任何一次响应都不受另一个租户数据或凭据的影响——新代码路径除了 `api_client.py` 里既有的按请求传递的客户端/租户机制之外，不引入任何新的共享或跨请求状态。

### 范围切分

- **本单（MVP）**：给 `mspbots_forms_form_get` 加上单题目过滤（AC1-AC4、AC6，现在就能自动化测试）；AC5 是手工、真实环境检查，等代码上线到有真实租户数据的环境后再跑一次。
- **明确不在本单范围 / 留给以后**：把精简投影 `include=["questions"]` 扩展成对所有调用方都带选项级属性；改后端 survey API 自己的体积上限；下游真正会为 SOP 230 R-07 调用这个新参数的 skill 配置消费方（那是另一块工作，不属于这个 MCP 工具，也不属于本单）。

### Open Questions

- **[已假设]** 提单人当初观察到的截断，到底是 `include=["questions"]` 精简模式（本来设计上就不带选项属性）造成的，还是 `include=["definition"]` 触发了 `dump_json_capped` 的体积截断——这一点没有确认，本沙箱没有真实环境可复现。假设：不管是哪一种都不重要，因为本设计的修复方案（一个专门的单题目过滤，见技术设计）对目标题目会绕开这两条路径,不管原始症状是哪条路径造成的。不阻塞；如果以后真实复现发现是第三种、无关的机制，需要重新考虑的也只是技术设计的改动清单，不影响这份产品设计。
- **[已假设]** 这个参数按 SurveyJS 的 `name` 属性匹配题目（例如 `"client_org"`），这既符合提单人提到它的方式，也符合 `mspbots_forms_form_update` 文档里已经用 `name` 作为逐题标识符的先例（`forms.py:159-163`）。如果产品希望改成按题目 `title` 文案匹配，那是同一改动上的一个更小的后续调整。
- **[不阻塞]** f7528a78 之外的其它大表单是否也会撞到同样的症状，假设是会的（同一条代码路径服务所有表单），所以修复是通用于所有表单写的，不是针对 f7528a78 的特例。

## 技术设计

### 结论

给 `mspbots_forms_form_get`（`forms.py:60-87`）加一个可选参数 `field_id`。传了这个参数时，始终向后端请求完整的 `include=definition`，通过遍历 definition 的 page/element 树（含嵌套的 `panel` 元素）找到 SurveyJS `name` 与 `field_id` 匹配的那一个题目，并把这个题目自身的字段平铺在结果顶层返回（不嵌套在包装键下面），这样 `dump_json_capped` 既有的顶层列表截断逻辑在 `choices` 数组异常大时仍能正确生效。不改后端、不改数据库、不改其它工具。

### 现有实现定位

- `src/mspbots_forms_mcp/tools/forms.py:60-87` —— `mspbots_forms_form_get`，本次要扩展的工具。
- `src/mspbots_forms_mcp/tools/forms.py:66-69` —— 现有 `include` 语义（`definition`/`questions`/`versions`），本设计不改动它。
- `src/mspbots_forms_mcp/_json.py:18-61` —— `dump_json_capped`，原样复用；它的顶层列表截断行为正是本设计依赖的、在需要时正确裁剪超大 `choices` 数组的机制（AC2）。
- `src/mspbots_forms_mcp/api_client.py:118-119` —— `FormsAPIClient.get`，原样用来取 `include=definition`。
- `src/mspbots_forms_mcp/tools/forms.py:159-163` —— 仓库里最接近的、用 `name` 标识一个题目的先例（在 `mspbots_forms_form_update` 的文档里），用来支撑上面 Open Questions 里"`field_id` = SurveyJS `name`"这个选择。
- 本仓库没有数据库层（它是一个包在外部 REST API 上的薄 MCP 封装；`api_client.py` 就是全部的数据访问层）——对这次改动而言，"现有实现定位"就只有这两个文件。

### 方案选型

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A —— 单题目过滤（`field_id` 参数） | 取完整 definition，只返回匹配题目的字段，平铺在顶层 | 对任意大小的表单都能解决问题；与提单人自己建议的修复方向一致（"a field_id filter returning one field with all option properties"）；改动小、只在本仓库内自成一体 | 需要遍历 SurveyJS 元素树（pages → elements，含嵌套 panel 元素），而这个形状按文件自己的文档说明尚未独立对照真实后端验证过，只做过一次 2026-08-07 的冒烟测试 | **采用** |

### 数据与接口契约

**工具参数（MCP 层面，不是 REST——这是进程内 Python 函数签名的改动）**

- 新增：`mspbots_forms_form_get` 上的 `field_id: str | None = None`。向后兼容——不传时行为与今天完全一致。
- 语义：匹配表单 `definition` 里某个 SurveyJS 题目元素的 `"name"` 属性（见上面关于 `name` 还是 `title` 的 Open Question）。

**后端 REST 调用（端点不变，和今天一样）**

- `GET {base}/surveys/{form_id}?include=definition`（以及调用方同时传的其它 `include` 值，去重后一起带上）——还是 `api_client.py` 今天已经在调的那个端点；只是在 `field_id` 存在时调整传入的 `include` 值。

**工具响应形状**

- 不传 `field_id`（今天的情况，不变）：`include` 今天产出什么形状，照样经 `dump_json_capped` 返回。
- 传了 `field_id`、找到题目：
  ```json
  {
    "form_id": "f7528a78",
    "field_id": "client_org",
    "name": "client_org",
    "title": "Client Organization",
    "type": "dropdown",
    "choices": [
      {"value": "...", "text": "...", "tenantId": "...", "haloClientId": "...", "rewstOrgId": "..."}
    ]
  }
  ```
  **这是设计要求，不是建议**：这个题目自身的字段（包括 `choices`）必须平铺在这个 dict 的**顶层**，不能嵌套成 `{"question": {...}}`。`dump_json_capped` 的截断只扫描顶层 dict 键里值为 `list` 的那些（`_json.py:31`）——如果 `choices` 嵌套在 `"question"` 键下面深一层，一个异常大的 `choices` 数组就不会被发现、不会被裁剪；整个响应反而会落进"太大、又不是列表形状"的分支，被整体丢弃，原样重现这张工单要修的那个 bug。上面这种平铺形状，正是 AC2 成立的前提。
- 传了 `field_id`、没找到题目：`error_envelope("not_found", "No question named '<field_id>' in form <form_id>", False)`——和本文件里其它每条错误已经在用的 JSON 形状一致（`api_client.py` → `FormsAPIError.to_envelope()`，或直接用 `_json.error_envelope`，与 `forms.py:266-269` 既有的模式一致）。

**向后兼容**：纯增量。不改变任何现有调用方的请求或响应形状。

### 关键流程时序

```
agent -> mspbots_forms_form_get(form_id, field_id="client_org")
      -> client_factory() -> FormsAPIClient（不变）
      -> client.get(f"/surveys/{form_id}", params={"include": "definition"})   # 传了 field_id 时强制如此
      -> 后端返回完整 SurveyJS definition（后端调用不变）
      -> find_question_by_name(definition, "client_org")   # 新辅助函数，遍历 pages/elements（含嵌套 panel）
            -> 找到：题目 dict
            -> 没找到：None
      -> 找到：dump_json_capped({"form_id": ..., "field_id": ..., **question})
      -> 没找到：error_envelope("not_found", ...)
      <- 单题目 JSON（或错误）返回给调用方
```

### 非功能

- **幂等与并发**：`mspbots_forms_form_get` 本来就是只读的（`ToolAnnotations(readOnlyHint=True)`，`forms.py:59`）；新代码路径不加任何写操作、不加任何新状态，所以天然幂等，并发调用下也安全。
- **性能**：每次调用还是一次后端 GET，和今天一样（不引入 N+1）——传了 `field_id` 时会强制用 `include=definition` 而不是更轻量的 `include` 值，上游载荷会比 `include=questions` 稍大一些，但只取一次、在客户端过滤；不增加额外的往返。
- **安全**：没有新的鉴权面；原样复用既有的 `FormsAPIClient`（API key header + `X_Tenant_ID` cookie，`api_client.py:103-111`）。这次改动不会让任何调用方看到比今天 `include=definition` 已经会返回的更多数据——只是改变了调用方能请求到这份数据里的哪一"片"。
- **多租户隔离**：不受影响——见 AC6。新的辅助函数（`find_question_by_name`）是个纯函数，只操作传进来的、已经过租户限定的 `definition` dict；它本身不跨调用保存状态，也不读取任何租户/凭据数据。
- **可观测性**：本次改动涉及的文件里本仓库没有日志框架（已核实——`forms.py`/`api_client.py` 都没有 `logging` 的 import）；与此一致，这次改动也不新增日志。如果以后有单子给这个仓库加结构化日志，到时候应该把这条新错误路径也补上日志——不在本单范围内。
